Configurer Azure App Service

Créer une appli web, CI/CD, emplacements de déploiement et échanges, authentification intégrée, domaine personnalisé et TLS, sauvegarde et Application Insights. Les notions marquées ➕ examen complètent le module.

⏱ Lecture : 10 min · module complet 🎯 Ce qui est échangé ou non au swap : question fréquente
💡
À retenir : App Service héberge applis web, API et mobiles sans gérer d'OS. Les emplacements (Standard et +) permettent de tester puis échanger sans coupure ; le domaine, l'échelle, Always On et les restrictions IP restent sur place, les paramètres suivent sauf « paramètre d'emplacement ». Domaine : CNAME ou A + TXT. Sauvegarde : compte de stockage, 10 Go max.

Pour s'en souvenir : le quai de livraison 🚛

🔁 Emplacements de déploiement

  • Production = le quai 1 où les clients viennent chercher leur marchandise
  • Staging = le quai 2 où on prépare et vérifie le nouveau chargement
  • Échange (swap) = on change les panneaux des quais : le quai 2 devient le quai 1, sans arrêter le service
  • Problème ? On rééchange : l'ancien chargement attend encore au quai 2

🏷️ Ce qui reste collé au quai

  • Le chargement (le code, les paramètres d'appli) change de quai
  • L'enseigne du quai (domaine perso), les règles d'accès (restrictions IP), le nombre de caristes (mise à l'échelle) restent au quai
  • Un paramètre coché « paramètre d'emplacement » = une étiquette vissée au quai

1 · App Service et la création d'une appli

🌐 Ce qu'il héberge

  • Applis web, API et back-ends mobiles, sur Windows ou Linux (PaaS : pas d'OS à gérer)
  • ASP.NET/.NET, Java, Node.js, PHP, Python, ou un conteneur Docker
  • Mise à l'échelle manuelle ou auto, SLA, conformité ISO/SOC/PCI
  • Connexion Entra ID ou Google, Facebook, X, Microsoft ; restrictions IP ; identités managées ; CORS intégré
  • Modèles Marketplace : WordPress, Drupal, Joomla

🛠️ À la création

  • Nom unique → monappli.azurewebsites.net
  • Publier : code ou conteneur Docker
  • Pile d'exécution et version (+ commande de démarrage pour Linux)
  • OS, région, plan App Service

⚙️ Après, dans Configuration

  • Always On : garde l'appli chargée sans trafic (obligatoire pour les WebJobs continus ou CRON)
  • Affinité de session (ARR) : un client reste sur la même instance
  • HTTPS uniquement : redirige HTTP vers HTTPS

3 · Les emplacements de déploiement

✅ Pourquoi

  • Chaque emplacement = une vraie appli avec son propre nom d'hôte
  • Valider en staging avant la prod
  • Zéro coupure : la cible est préchauffée avant l'échange, aucune requête perdue
  • Retour arrière : rééchanger
  • Échange automatique : chaque push dans staging part en prod après le préchauffage (➕ pas sur Linux)
  • Niveaux : Standard (5), Premium (20), Isolated
  • Nouvel emplacement : vide ou cloné d'un autre

🔀 Ce qui part et ce qui reste

Échangé avec le codeReste sur l'emplacement
Pile et version, 32/64 bitsDomaines personnalisés
Paramètres d'appli *Certificats non publics, réglages TLS
Chaînes de connexion *Mise à l'échelle
Comptes de stockage montés *Always On
Certificats publicsRestrictions IP, CORS
Contenu des WebJobsPlanificateurs WebJobs, diagnostics
Mappages de cheminsIntégration au réseau virtuel, identités managées

* sauf si tu coches Paramètre d'emplacement : il reste alors sur place (ex. la chaîne vers la BD de test).

4 · Sécuriser l'appli

  • Authentification intégrée (« Easy Auth ») : un module tourne à côté de l'appli, sans code ni SDK. Il connecte l'usager au fournisseur, gère les jetons et la session, et met l'identité dans les en-têtes HTTP.
  • Fournisseurs : Microsoft Entra ID, Microsoft, Google, Facebook, X.
  • Autoriser les requêtes anonymes : le code de l'appli décide (bon pour un site avec une page d'accueil publique).
  • Exiger l'authentification : redirection vers /.auth/login/<fournisseur>, ou HTTP 401 pour une appli mobile native. Bloque tout, y compris la page d'accueil.
  • Journaux : chercher EasyAuthModule_32/64 dans le suivi des demandes ayant échoué.

5 · Nom de domaine personnalisé

  1. Réserver le domaine : l'acheter dans le portail Azure (le plus simple) ou chez un registraire.
  2. Créer l'enregistrement DNS : CNAME www → optiweb.azurewebsites.net (suit l'appli si son IP change) ou A vers l'IP de l'appli (obligatoire pour l'apex optifuel.cloud, à mettre à jour si l'IP change). ➕ Plus un TXT asuid qui prouve que le domaine est à toi.
  3. Activer le domaine dans le portail (validation), puis ajouter une liaison TLS : certificat managé App Service gratuit, renouvelé tout seul 30 jours avant l'expiration.

7 · Application Insights

Fonction d'Azure Monitor qui surveille une appli en production et détecte seule les anomalies de performance (.NET, Node.js, Java ; Azure, local ou autre cloud).

  • Requêtes : taux, temps de réponse, échecs, pages populaires, heures de pointe, lieux
  • Dépendances : un service externe ralentit-il l'appli ?
  • Exceptions serveur et navigateur ; vues de page et temps de chargement
  • Sessions et usagers ; compteurs CPU, mémoire, réseau ; diagnostics Docker
  • Traces liées aux requêtes ; événements personnalisés (ex. pleins de carburant saisis)
  • Sorties : alertes, Power BI, Visual Studio

8 · Le labo 09a en bref

  1. Créer une appli web (PHP, Windows).
  2. Créer un emplacement staging.
  3. Configurer le déploiement (Centre de déploiement).
  4. Déployer le code dans staging.
  5. Échanger staging et production.
  6. Configurer et tester la mise à l'échelle auto.

9 · ➕ En CLI

az webapp create -g rg-labo -p plan-web -n optiweb123 --runtime "NODE:20-lts"
az webapp config set -g rg-labo -n optiweb123 --always-on true
az webapp update -g rg-labo -n optiweb123 --https-only true
az webapp deployment slot create -g rg-labo -n optiweb123 --slot staging
az webapp deployment slot swap -g rg-labo -n optiweb123 --slot staging --target-slot production
az webapp config appsettings set -g rg-labo -n optiweb123 --slot staging \
  --slot-settings DB_URL="postgres://test..."      # paramètre d'emplacement
az webapp config hostname add -g rg-labo --webapp-name optiweb123 --hostname www.exemple.com

🚛 Appliquer à Optifuel

Ce qui colle à Optifuel :

  • Next.js tourne sur App Service Linux (pile Node) ou en conteneur.
  • Ton workflow GitHub Actions déploie dans staging, tu testes, puis swap en prod.
  • La chaîne PostgreSQL de test = paramètre d'emplacement, pour ne jamais brancher staging sur la vraie base.
  • Application Insights pour voir les pages lentes de l'appli.

Pièges d'examen

🪤« Après le swap, mon domaine perso est passé sur staging. »Les domaines personnalisés restent sur leur emplacement, comme l'échelle, Always On et les restrictions IP.
🪤« Ma chaîne de connexion de test est partie en prod au swap. »Les chaînes de connexion sont échangées par défaut. Coche Paramètre d'emplacement.
🪤« Je crée un emplacement staging sur mon plan Basic. »Emplacements à partir de Standard.
🪤« Je pointe optifuel.cloud (l'apex) avec un CNAME. »Beaucoup de registraires refusent un CNAME à l'apex : enregistrement A (+ TXT de vérification).
🪤« Je sauvegarde vers mon compte de stockage protégé par pare-feu. »Un compte avec pare-feu ne peut pas servir de destination de sauvegarde.
🪤« Je veux sauvegarder un site de 25 Go. »Limite : 10 Go appli + base.
🪤« J'exige l'authentification et ma page d'accueil publique reste visible. »« Exiger l'authentification » bloque tout. Autorise l'anonyme et gère-le dans le code.
🪤« Mes WebJobs CRON s'arrêtent la nuit. »Active Always On : sans lui l'appli se décharge quand il n'y a pas de trafic.

🟪 Appli web Linux + emplacement staging

resource "azurerm_linux_web_app" "web" {
  name                = "optiweb123"
  resource_group_name = azurerm_resource_group.labo.name
  location            = "eastus"
  service_plan_id     = azurerm_service_plan.web.id
  https_only          = true
  site_config {
    always_on = true
    application_stack {
      node_version = "20-lts"
    }
  }
  app_settings = {
    "NODE_ENV" = "production"
  }
  sticky_settings {
    app_setting_names = ["DB_URL"]   # paramètre d'emplacement
  }
}
resource "azurerm_linux_web_app_slot" "staging" {
  name           = "staging"
  app_service_id = azurerm_linux_web_app.web.id
  site_config {
    application_stack {
      node_version = "20-lts"
    }
  }
}
