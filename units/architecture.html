Les composants architecturaux d'Azure

Où vivent physiquement tes ressources (régions, zones) et comment on les range (groupes d'administration, abonnements, groupes de ressources).

⏱ Lecture : 8 min · module complet 🎯 Base de tout l'AZ-104 (et de l'AZ-900)
💡
À retenir : physique = centre de données → zone de disponibilité → région → paire de régions. Gestion = ressource → groupe de ressources → abonnement → groupe d'administration. Tout ce que tu fais dans Azure se place sur ces deux échelles.

Pour s'en souvenir : le réseau de terminaux 🚛

🏗️ L'infrastructure physique

  • Centre de données = un entrepôt
  • Zone de disponibilité = un terminal avec sa propre électricité, son refroidissement et son réseau. Si un terminal brûle, les autres roulent
  • Région = la ville qui regroupe ses terminaux (Toronto = Canada Central)
  • Paire de régions = le terminal de secours dans une autre ville du même pays (Toronto ↔ Québec)
  • Région souveraine = une cour sous douane réservée au gouvernement

🗂️ La gestion

  • Ressource = une palette (une VM, un compte de stockage…)
  • Groupe de ressources = la remorque : on y charge ce qui part et revient ensemble. On décroche la remorque, tout part avec
  • Abonnement = le contrat client : une facture et des règles d'accès
  • Groupe d'administration = la division (Canada, É.-U.) qui impose ses règles à tous ses contrats

1 · L'infrastructure physique

ÉlémentCe qu'il faut savoir
Centre de donnéesBâtiment avec serveurs, électricité, refroidissement et réseau. Tu ne le choisis jamais directement
RégionUn ou plusieurs centres de données proches, reliés par un réseau à faible latence. C'est toi qui choisis la région d'une ressource. Certains services ou tailles de VM n'existent que dans certaines régions
Zone de disponibilitéCentres de données physiquement séparés dans une région, avec électricité, refroidissement et réseau indépendants. Minimum 3 dans les régions qui en ont. Toutes les régions n'en ont pas
Paire de régionsDeux régions de la même géographie, idéalement à ≈ 300 milles et plus l'une de l'autre. Mises à jour Azure une région à la fois, reprise prioritaire d'une des deux en cas de panne majeure, données gardées dans la même géographie (sauf Brésil Sud)
Région souveraineInstances isolées d'Azure pour les gouvernements : US Gov (Virginie, Iowa…) et Chine (exploitée par 21Vianet, pas par Microsoft)

Comment un service utilise les zones

Zonal

📌 Épinglé à une zone

Tu choisis la zone : VM, disque managé, IP publique. Pour la haute dispo, tu en déploies plusieurs, une par zone.

Redondant interzone

🔁 Répliqué automatiquement

Azure copie lui-même dans plusieurs zones : stockage ZRS, Azure SQL Database.

Non régional

🌍 Toujours disponible

Service mondial, résilient aux pannes de zone et de région : Entra ID, Front Door, Traffic Manager.

🇨🇦 Pour toi : Canada Central (Toronto) et Canada East (Québec) forment une paire. Canada Central a des zones de disponibilité, Canada East n'en a pas. C'est pour ça que canadacentral est le meilleur choix pour tes labos sur la haute disponibilité.

NiveauRègles à connaître
RessourceInstance d'un service (VM, VNet, base de données…). Appartient à un seul groupe de ressources
Groupe de ressourcesConteneur logique. Pas d'imbrication (pas de groupe dans un groupe). Une ressource peut être déplacée vers un autre groupe. Supprimer le groupe supprime tout ce qu'il contient. Les droits (RBAC) donnés au groupe s'appliquent à ses ressources. Bonne pratique : regrouper ce qui a le même cycle de vie
AbonnementUnité de facturation et de contrôle d'accès. On en crée plusieurs pour séparer les environnements (dev/test/prod), les équipes ou les factures. Chacun a ses limites (quotas)
Groupe d'administrationRegroupe des abonnements pour appliquer Azure Policy et RBAC à tous d'un coup. Jusqu'à 10 000 par annuaire, arborescence de 6 niveaux de profondeur (sans compter la racine et les abonnements). Chaque groupe ou abonnement a un seul parent

🔽 Héritage : une stratégie ou un rôle posé en haut descend jusqu'aux ressources. Exemple : « seulement les régions canadiennes » sur le GA Production s'applique à tous ses abonnements, groupes et ressources.

Hiérarchie de base : un compte Azure peut avoir plusieurs abonnements, et chaque abonnement contient des groupes de ressources.

Pièges d'examen

🪤« Je mets un groupe de ressources dans un autre groupe de ressources. »Impossible. Pas d'imbrication. Pour une hiérarchie, ce sont les groupes d'administration qui s'imbriquent.
🪤« Une VM peut appartenir à deux groupes de ressources. »Non, un seul. On peut la déplacer.
🪤« Toutes les régions Azure ont des zones de disponibilité. »Faux. Exemple : Canada East n'en a pas.
🪤« Pour séparer la facturation du marketing et des TI, je crée deux groupes de ressources. »Non. L'unité de facturation, c'est l'abonnement (les étiquettes aident à ventiler, mais la frontière, c'est l'abonnement).
🪤« Une ressource doit être dans la même région que son groupe de ressources. »Faux. La région du groupe stocke seulement ses métadonnées. Ses ressources peuvent être ailleurs.
🪤« Je veux appliquer une stratégie à 50 abonnements d'un coup : je l'attache à chacun. »Non. Regroupe-les dans un groupe d'administration et attache-la une fois, l'héritage fait le reste.

🟪 La hiérarchie et les zones en code

# Groupe d'administration + rattachement d'un abonnement
resource "azurerm_management_group" "labo" {
  display_name = "Labo"
}

resource "azurerm_management_group_subscription_association" "essai" {
  management_group_id = azurerm_management_group.labo.id
  subscription_id     = "/subscriptions/${var.subscription_id}"
}

# Groupe de ressources : la région ne sert qu'aux métadonnées
resource "azurerm_resource_group" "labo" {
  name     = "rg-labo-archi"
  location = "canadacentral"
}

# Service zonal : la VM est épinglée à la zone 1
resource "azurerm_linux_virtual_machine" "vm1" {
  # name, size, network_interface_ids, os_disk…
  zone = "1"
}

# Service redondant interzone : stockage ZRS
resource "azurerm_storage_account" "zrs" {
  # name, resource_group_name, location…
  account_tier             = "Standard"
  account_replication_type = "ZRS"
}
