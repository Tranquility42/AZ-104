Les modèles ARM : structure et déploiement

Un fichier JSON qui décrit ce que tu veux dans Azure. Resource Manager se charge du comment.

⏱ Lecture : 6 min 🎯 Domaine examen : Déployer et gérer les ressources 🟪 Lien direct avec Terraform
💡
À retenir : un modèle ARM est un fichier JSON déclaratif. Il a 3 sections obligatoires : $schema, contentVersion et resources. Il est idempotent, validé avant le déploiement, et ses ressources sont créées en parallèle quand c'est possible. On le déploie avec az deployment group create.

Pour s'en souvenir : le bon de commande 🚛

🗺️ Impératif = dicter l'itinéraire

« Prends la 20 Est, sortie 115, tourne à droite, recule au quai 7, décharge 20 palettes. » Tu donnes chaque étape dans l'ordre. Si une étape échoue, tout s'arrête au milieu.

= un script Azure CLI / PowerShell : une commande, puis une autre…

📋 Déclaratif = le bon de commande

« 20 palettes au quai 7 avant 8 h. » Le répartiteur (Resource Manager) choisit l'ordre, envoie plusieurs camions en parallèle et vérifie le bon avant le départ.

= un modèle ARM : tu décris le résultat final.

🔁 Idempotence : le bon envoyé deux fois

Si tu renvoies le même bon de commande, le répartiteur voit qu'il y a déjà 20 palettes au quai 7 et il ne fait rien. Tu as toujours 20 palettes, pas 40. C'est l'idempotence : même modèle déployé 10 fois, même état final.

Paramètres et variables : les paramètres sont les cases vides du bon (destination, quantité), remplies au moment de l'envoi. Les variables sont des calculs faits sur le bon lui-même (« quai = 7 + numéro de zone »), pour ne pas répéter les mêmes formules.

L'anatomie d'un modèle

Mnémo pour les 3 obligatoires, S·C·R : Schéma, ContentVersion, Ressources. Sans eux, le camion ne part pas.

{ "$schema": "https://schema.management.azure.com/ schemas/2019-04-01/deploymentTemplate.json#", "contentVersion": "1.0.0.1", "apiProfile": "", "parameters": {}, "variables": {}, "functions": [], "resources": [ { "type": "Microsoft.Storage/storageAccounts", "apiVersion": "2025-01-01", "name": "learntemplatestorage123", "location": "westus", "sku": { "name": "Standard_LRS" }, "kind": "StorageV2", "properties": { "supportsHttpsTrafficOnly": true } } ], "outputs": {} }
$schema
obligatoire
Où se trouve le schéma JSON qui décrit la structure. La version dépend de l'étendue du déploiement.
contentVersion
obligatoire
La version de ton modèle (ex. 1.0.0.0), pour être sûr de déployer le bon.
apiProfile
facultatif
Un lot de versions d'API, pour ne pas la répéter sur chaque ressource.
parameters
facultatif
Valeurs fournies au déploiement : fichier de paramètres, ligne de commande ou portail.
variables
facultatif
Valeurs réutilisées pour simplifier les expressions.
functions
facultatif
Fonctions définies par l'utilisateur, pour des expressions complexes répétées.
resources
obligatoire
Ce qu'on déploie ou met à jour, dans un groupe de ressources ou un abonnement.
outputs
facultatif
Valeurs renvoyées à la fin du déploiement.
🏷️ Type de ressource = {fournisseur}/{type}. Exemple : Microsoft.Storage/storageAccounts, soit le fournisseur Microsoft.Storage et le type storageAccounts. Les propriétés disponibles sont listées par version d'API dans la référence learn.microsoft.com/azure/templates.

Pourquoi un modèle plutôt qu'un script

AvantageCe que ça veut dire
IdempotenceMême modèle déployé plusieurs fois, même état final
OrchestrationResource Manager crée les ressources dans le bon ordre, et en parallèle quand c'est possible, donc plus vite qu'un script
Un seul appelUn modèle = un appel à Resource Manager, un script = plusieurs appels
Validation intégréeLe modèle est vérifié avant le déploiement
ModularitéPetits modèles réutilisables, liés ou imbriqués
TraçabilitéHistorique, état, paramètres et sorties visibles dans le portail. Versionné dans Git comme du code
CI/CDDéploiement continu avec Azure Pipelines ou GitHub Actions

Déployer un modèle local (Azure CLI)

Se connecter
az login
Créer (ou réutiliser) un groupe de ressources
az group create --name rg-learn --location "canadaeast"
Lister les régions : az account list-locations. Région par défaut : az configure --defaults location=canadaeast
Déployer à l'étendue du groupe de ressources
templateFile="azuredeploy.json" az deployment group create \ --name blanktemplate \ --resource-group rg-learn \ --template-file $templateFile
Le nom du déploiement permet de le retrouver dans l'historique. PowerShell : New-AzResourceGroupDeployment.

Trois façons de déployer : modèle local (cette unité), modèle lié (un modèle principal appelle des sous-modèles, stockés et protégés par un jeton SAS), ou depuis un pipeline CI/CD.

Pièges d'examen

🪤az group deployment create --resource-group …Ancienne commande, déconseillée. La bonne est az deployment group create : d'abord « deployment », puis l'étendue.
🪤« parameters est obligatoire. »Faux. Seuls $schema, contentVersion et resources sont obligatoires (S·C·R).
🪤« Redéployer le même modèle va créer des ressources en double. »Faux. C'est idempotent : même état final.
🪤« Un modèle ARM liste les commandes à exécuter dans l'ordre. »Non. C'est déclaratif : il décrit le résultat, et Resource Manager décide de l'ordre (et parallélise).
🪤« Le type d'un compte de stockage, c'est storageAccounts. »Incomplet. Il faut Microsoft.Storage/storageAccounts (fournisseur/type).
