Les modèles ARM : structure, paramètres et déploiement

Un fichier JSON qui décrit ce que tu veux dans Azure. Resource Manager se charge du comment.

⏱ Lecture : 10 min · module complet 🎯 Domaine examen : Déployer et gérer les ressources 🟪 Lien direct avec Terraform
💡
À retenir : un modèle ARM est un fichier JSON déclaratif. Il a 3 sections obligatoires : $schema, contentVersion et resources. Il est idempotent, validé avant le déploiement, et ses ressources sont créées en parallèle quand c'est possible. On le déploie avec az deployment group create. Les paramètres le rendent réutilisable, et les sorties renvoient des infos après le déploiement.

Pour s'en souvenir : le bon de commande 🚛

🗺️ Impératif = dicter l'itinéraire

« Prends la 20 Est, sortie 115, tourne à droite, recule au quai 7, décharge 20 palettes. » Tu donnes chaque étape dans l'ordre. Si une étape échoue, tout s'arrête au milieu.

= un script Azure CLI / PowerShell : une commande, puis une autre…

📋 Déclaratif = le bon de commande

« 20 palettes au quai 7 avant 8 h. » Le répartiteur (Resource Manager) choisit l'ordre, envoie plusieurs camions en parallèle et vérifie le bon avant le départ.

= un modèle ARM : tu décris le résultat final.

🔁 Idempotence : le bon envoyé deux fois

Si tu renvoies le même bon de commande, le répartiteur voit qu'il y a déjà 20 palettes au quai 7 et il ne fait rien. Tu as toujours 20 palettes, pas 40. C'est l'idempotence : même modèle déployé 10 fois, même état final.

Paramètres et variables : les paramètres sont les cases vides du bon (destination, quantité), remplies au moment de l'envoi. Les variables sont des calculs faits sur le bon lui-même (« quai = 7 + numéro de zone »), pour ne pas répéter les mêmes formules.

L'anatomie d'un modèle

Mnémo pour les 3 obligatoires, S·C·R : Schéma, ContentVersion, Ressources. Sans eux, le camion ne part pas.

{ "$schema": "https://schema.management.azure.com/ schemas/2019-04-01/deploymentTemplate.json#", "contentVersion": "1.0.0.1", "apiProfile": "", "parameters": {}, "variables": {}, "functions": [], "resources": [ { "type": "Microsoft.Storage/storageAccounts", "apiVersion": "2025-01-01", "name": "learntemplatestorage123", "location": "westus", "sku": { "name": "Standard_LRS" }, "kind": "StorageV2", "properties": { "supportsHttpsTrafficOnly": true } } ], "outputs": {} }
$schema
obligatoire
Où se trouve le schéma JSON qui décrit la structure. La version dépend de l'étendue du déploiement.
contentVersion
obligatoire
La version de ton modèle (ex. 1.0.0.0), pour être sûr de déployer le bon.
apiProfile
facultatif
Un lot de versions d'API, pour ne pas la répéter sur chaque ressource.
parameters
facultatif
Valeurs fournies au déploiement : fichier de paramètres, ligne de commande ou portail.
variables
facultatif
Valeurs réutilisées pour simplifier les expressions.
functions
facultatif
Fonctions définies par l'utilisateur, pour des expressions complexes répétées.
resources
obligatoire
Ce qu'on déploie ou met à jour, dans un groupe de ressources ou un abonnement.
outputs
facultatif
Valeurs renvoyées à la fin du déploiement.
🏷️ Type de ressource = {fournisseur}/{type}. Exemple : Microsoft.Storage/storageAccounts, soit le fournisseur Microsoft.Storage et le type storageAccounts. Les propriétés disponibles sont listées par version d'API dans la référence learn.microsoft.com/azure/templates.

Déployer un modèle local (Azure CLI)

Se connecter
az login
Créer (ou réutiliser) un groupe de ressources
az group create --name rg-learn --location "canadaeast"
Lister les régions : az account list-locations. Région par défaut : az configure --defaults location=canadaeast
Déployer à l'étendue du groupe de ressources
templateFile="azuredeploy.json" az deployment group create \ --name blanktemplate \ --resource-group rg-learn \ --template-file $templateFile
Le nom du déploiement permet de le retrouver dans l'historique. PowerShell : New-AzResourceGroupDeployment.

Trois façons de déployer : modèle local (cette unité), modèle lié (un modèle principal appelle des sous-modèles, stockés et protégés par un jeton SAS), ou depuis un pipeline CI/CD.

Paramètres et sorties : rendre le modèle flexible

Un modèle avec un nom et un SKU écrits en dur ne déploie qu'un seul compte, toujours pareil. Avec des paramètres, le même modèle sert en dev, en test et en prod.

"parameters": { "storageSKU": { "type": "string", "defaultValue": "Standard_LRS", "allowedValues": [ "Standard_LRS", "Standard_GRS", "Standard_ZRS", "Premium_LRS" ], "metadata": { "description": "Type de stockage" } }, "storageName": { "type": "string", "minLength": 3, "maxLength": 24 } } // utilisation dans la ressource : "name": "[parameters('storageName')]", "sku": { "name": "[parameters('storageSKU')]" }
type
obligatoire
string, int, bool, object, array, secureString, secureObject
defaultValue
Valeur utilisée si on ne fournit rien. Sans elle, le paramètre est obligatoire.
allowedValues
La liste fermée des valeurs acceptées. Une autre valeur (ex. Basic) fait échouer la validation avant tout déploiement.
minLength / maxLength
Longueur d'une chaîne ou d'un tableau
minValue / maxValue
Bornes d'un entier
metadata
description affichée dans le portail

✅ Bonnes pratiques

  • Paramètre pour ce qui change selon l'environnement : SKU, taille, capacité, noms
  • Une description et une valeur par défaut dès que possible
  • Mots de passe et secrets en secureString, objets sensibles en secureObject. On ne peut pas les relire après le déploiement
  • Jamais de valeur par défaut pour un utilisateur ou un mot de passe, et rien d'écrit en dur
  • Maximum 256 paramètres par modèle

📤 Les sorties (outputs)

"outputs": { "storageEndpoint": { "type": "object", "value": "[reference(parameters('storageName')) .primaryEndpoints]" } }

Seuls type et value servent en pratique. condition (n'afficher que si vrai) et copy (plusieurs valeurs) sont facultatifs. reference() lit l'état réel de la ressource après sa création, ici ses URL blob, file, queue et table.

Passer les valeurs au déploiement

# Azure CLI az deployment group create \ --name addSkuParameter \ --template-file azuredeploy.json \ --parameters storageSKU=Standard_GRS storageName=stmah2026
# Azure PowerShell : chaque paramètre du # modèle devient un paramètre de la commande New-AzResourceGroupDeployment ` -Name addSkuParameter ` -TemplateFile azuredeploy.json ` -storageName stmah2026 -storageSKU Standard_GRS
🎲
Astuce de ton labo (hors de l'unité) : pour ne plus tomber sur StorageAccountAlreadyTaken, donne au nom une valeur par défaut calculée : "[concat('stlearn', uniqueString(resourceGroup().id))]". uniqueString fabrique un code de 13 caractères à partir de l'identifiant du groupe de ressources. Il est unique dans Azure et toujours le même pour ce groupe, donc le déploiement reste idempotent.

Les exercices en un coup d'œil

Chaque déploiement porte un nom et apparaît dans l'historique du groupe de ressources (portail → groupe → Déploiements). Les ressources déjà là ne sont pas recréées, seules les différences sont appliquées.

#DéploiementCe qui change dans le modèleRésultat
1blanktemplateModèle vide (toutes les sections, aucune ressource)✅ réussi, 0 ressource
2addstorage+ un compte de stockage, nom écrit en dur✅ compte créé
3addnameparameterLe nom devient le paramètre storageName (3-24 caractères)✅ un nom déjà utilisé met à jour au lieu de créer
4addSkuParameter+ paramètre storageSKU avec allowedValues✅ Standard_GRS · ❌ Basic refusé à la validation
5addOutputs+ sortie storageEndpoint via reference()✅ les URL s'affichent dans le terminal et le portail
🧯 Les erreurs que tu as vraiment rencontrées
  • StorageAccountAlreadyTaken : le nom d'un compte de stockage est unique dans tout Azure, et learntemplatestorage123 est pris par d'autres élèves.
  • Nom invalide : 3 à 24 caractères, minuscules et chiffres seulement. Learn mentionne les tirets, mais Azure les refuse pour les comptes de stockage.
  • ReadOnlyDisabledSubscription : l'abonnement était annulé, donc en lecture seule. On l'a réglé en le réactivant. Pour nettoyer, on supprime le groupe de ressources, jamais l'abonnement.
  • Dans Cloud Shell, code ouvre un tunnel VS Code au lieu d'un éditeur. Utilise plutôt nano ou VS Code en local.

💡 Dans VS Code, Alt+Maj+F formate le JSON. Les modèles ARM acceptent les commentaires // et /* */.

Pièges d'examen

🪤az group deployment create --resource-group …Ancienne commande, déconseillée. La bonne est az deployment group create : d'abord « deployment », puis l'étendue.
🪤« parameters est obligatoire. »Faux. Seuls $schema, contentVersion et resources sont obligatoires (S·C·R).
🪤« Redéployer le même modèle va créer des ressources en double. »Faux. C'est idempotent : même état final.
🪤« Un modèle ARM liste les commandes à exécuter dans l'ordre. »Non. C'est déclaratif : il décrit le résultat, et Resource Manager décide de l'ordre (et parallélise).
🪤« Le type d'un compte de stockage, c'est storageAccounts. »Incomplet. Il faut Microsoft.Storage/storageAccounts (fournisseur/type).
🪤« Je mets le mot de passe admin en string avec une valeur par défaut. »Non. secureString, sans valeur par défaut.
🪤« minLength limite la valeur d'un entier. »Non. minLength/maxLength s'appliquent aux chaînes et tableaux, minValue/maxValue aux entiers.
🪤« Une valeur hors de allowedValues crée quand même la ressource avec un avertissement. »Non. Le déploiement échoue dès la validation, et rien n'est créé.
