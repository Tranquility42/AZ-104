Surveiller les VM avec Azure Monitor

Métriques de l'hôte, Metrics Explorer, alertes recommandées, journal d'activité, diagnostics de démarrage, VM Insights avec l'agent et collecte du Syslog par une DCR. Les notions marquées ➕ examen complètent le module.

⏱ Lecture : 8 min · module complet 🎯 Hôte vs invité, DCR, journal d'activité : questions fréquentes
💡
À retenir : l'hôte (CPU, disque, réseau) est surveillé sans agent. Pour l'intérieur de la VM (mémoire, Syslog, événements Windows) : agent AMA + DCR (quoi et où) + espace Log Analytics (requêtes KQL). Journal d'activité = qui a fait quoi. Diagnostics de démarrage = VM qui ne démarre pas.

Pour s'en souvenir : surveiller la flotte 🚛

📟 Ce qu'Azure voit tout seul (hôte)

  • Métriques de l'hôte = l'ordinateur de bord du camion : vitesse, régime moteur, carburant. Toujours là, sans rien installer
  • Journal d'activité = le registre du répartiteur : qui a démarré, arrêté ou modifié le camion
  • Diagnostics de démarrage = la photo du tableau de bord quand le camion ne démarre pas

🧑‍✈️ Ce qu'il faut installer (invité)

  • Agent Azure Monitor (AMA) = la boîte noire installée dans la cabine pour savoir ce qui se passe à l'intérieur (mémoire, disque, journaux de l'OS)
  • Règle de collecte (DCR) = la consigne : quoi noter et à quel bureau l'envoyer
  • Espace Log Analytics = le bureau des archives où on fouille avec KQL

1 · Données de l'hôte ou de l'invité ?

Hôte (plateforme)Invité (dans l'OS)
ExemplesCPU %, octets disque, réseau entrant/sortant, disponibilitéMémoire, espace disque logique, processus, journaux d'événements Windows, Syslog Linux
Agent ?Non, collecté d'officeOui : AMA + identité managée + DCR
Où les voirVM → Vue d'ensemble → Surveillance, Metrics ExplorerVM → Insights, Journaux (KQL)
➕ RétentionMétriques de plateforme : 93 joursLog Analytics : 30 jours par défaut, jusqu'à 2 ans (archive 12 ans)
➕ Piège classique : la mémoire utilisée d'une VM n'est pas une métrique de l'hôte. Pour la voir, il faut l'agent (VM Insights).

📤 Envoyer le journal d'activité ailleurs

Avec un paramètre de diagnostic vers :

  • Log Analytics : requêtes KQL et alertes (jusqu'à 2 ans, 12 ans en archive)
  • Compte de stockage : archive pas chère
  • Event Hubs : envoyer vers un outil hors Azure (SIEM)

➕ Sans export, le journal d'activité est gardé 90 jours.

⚠️ VM arrêtée = pas de données

Une VM arrêtée ne renvoie pas « 0 » mais rien (null). Une alerte de disponibilité ne détecte donc pas bien un arrêt. Pour savoir qui a arrêté ou désalloué la VM : une alerte sur le journal d'activité.

3 · VM Insights : les compteurs de l'invité

  1. Créer un espace de travail Log Analytics (de préférence dans la région de la VM).
  2. VM → Surveiller → Configurer : collecte basée sur les journaux, choisir ton espace de travail.
  3. Le portail installe l'agent (extension AzureMonitorLinuxAgent), active une identité managée et crée une DCR de performances.
  4. Attendre quelques minutes, vérifier l'extension dans Extensions + applications.
  5. Voir Insights → Performance (CPU, mémoire, disque logique) ou interroger la table InsightsMetrics.
InsightsMetrics
| where TimeGenerated > ago(30m)
| where Namespace == "Processor" and Name == "UtilizationPercentage"
| summarize CPU = avg(Val) by bin(TimeGenerated, 5m), Computer
| render timechart
Nouveau : les métriques OpenTelemetry envoient les compteurs invités vers un espace de travail Azure Monitor (requêtes PromQL, comme Prometheus), pas vers Log Analytics. La carte de VM Insights et le Dependency Agent seront retirés le 30 juin 2028.

4 · Collecter les journaux de l'OS (Syslog)

La DCR de VM Insights ne collecte pas le Syslog. On crée une deuxième DCR :

Réglage de la DCRExemple du labo
OùMoniteur → Règles de collecte des données → Créer
PlateformeLinux (Windows → source « Journaux d'événements Windows »)
RessourcesLa VM (on peut en associer plusieurs)
SourceSyslog Linux : user, daemon, syslog au niveau minimum Warning, le reste à NONE
DestinationAzure Monitor Logs, le même espace de travail

« Minimum Warning » = Warning et plus grave (Error, Critical…). Pour tester, sur la VM (Exécuter la commande, sans SSH) :

logger -p user.warning -t test "syslog test"     # sur la VM
# puis dans VM → Journaux :
Syslog
| where TimeGenerated > ago(30m) and SeverityLevel == "warning"
| project TimeGenerated, Computer, Facility, SyslogMessage

Rien n'arrive ? Vérifier la table Heartbeat : si l'agent répond, le problème est dans la DCR, sinon dans l'agent (extension, identité, réseau sortant).

5 · ➕ En CLI

az monitor log-analytics workspace create -g rg-labo -n law-labo -l eastus
az vm boot-diagnostics enable -g rg-labo -n web01
az vm boot-diagnostics get-boot-log -g rg-labo -n web01
az monitor metrics list --resource <id-vm> --metric "Percentage CPU" --interval PT5M -o table
az monitor activity-log list -g rg-labo --offset 1d -o table
az vm extension set -g rg-labo --vm-name web01 -n AzureMonitorLinuxAgent \
  --publisher Microsoft.Azure.Monitor --enable-auto-upgrade true

🚛 Appliquer à Optifuel

Pour la VM ou le nœud k3s d'Optifuel :

  • Métriques de l'hôte d'office : une alerte CPU et une alerte sur le journal d'activité (arrêt, suppression).
  • VM Insights pour la mémoire : PostgreSQL et Next.js en mangent, et l'hôte ne la voit pas.
  • Une DCR Syslog (daemon en Warning) pour voir les erreurs de k3s et de PostgreSQL au même endroit.

Pièges d'examen

🪤« Je vois la mémoire utilisée de ma VM dans les métriques de l'hôte. »La mémoire est une donnée de l'invité : il faut l'agent AMA (VM Insights).
🪤« J'installe l'agent, ça suffit pour collecter le Syslog. »Il faut une DCR qui dit quoi collecter et où l'envoyer. La DCR de VM Insights ne prend pas le Syslog.
🪤« Je veux savoir qui a supprimé la VM hier : Metrics Explorer. »C'est le journal d'activité (plan de contrôle).
🪤« Ma VM ne démarre plus, je me connecte en SSH pour voir. »Impossible si elle ne démarre pas : diagnostics de démarrage (capture d'écran + journal série).
🪤« Une alerte de disponibilité à 0 détecte l'arrêt de la VM. »VM arrêtée = aucune donnée (null). Utilise une alerte sur le journal d'activité.
🪤« Les métriques OpenTelemetry vont dans mon espace Log Analytics. »Elles vont dans un espace de travail Azure Monitor (PromQL).
🪤« Je garde mon journal d'activité 5 ans sans rien faire. »➕ 90 jours par défaut. Pour plus : paramètre de diagnostic vers Log Analytics ou un compte de stockage.

🟪 Espace Log Analytics + DCR Syslog

resource "azurerm_log_analytics_workspace" "labo" {
  name                = "law-labo"
  resource_group_name = azurerm_resource_group.labo.name
  location            = "eastus"
  sku                 = "PerGB2018"
  retention_in_days   = 30
}
resource "azurerm_monitor_data_collection_rule" "syslog" {
  name                = "collect-events-linux"
  resource_group_name = azurerm_resource_group.labo.name
  location            = "eastus"
  destinations {
    log_analytics {
      name                  = "law"
      workspace_resource_id = azurerm_log_analytics_workspace.labo.id
    }
  }
  data_flow {
    streams      = ["Microsoft-Syslog"]
    destinations = ["law"]
  }
  data_sources {
    syslog {
      name           = "syslog-warning"
      facility_names = ["user", "daemon", "syslog"]
      log_levels     = ["Warning", "Error", "Critical", "Alert", "Emergency"]
      streams        = ["Microsoft-Syslog"]
    }
  }
}
resource "azurerm_monitor_data_collection_rule_association" "vm" {
  name                    = "dcr-vm"
  target_resource_id      = azurerm_linux_virtual_machine.web.id
  data_collection_rule_id = azurerm_monitor_data_collection_rule.syslog.id
}
