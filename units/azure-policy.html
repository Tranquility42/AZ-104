Azure Policy et les initiatives

Des règles écrites en JSON qui vérifient, bloquent ou corrigent tes ressources Azure, appliquées à grande échelle grâce à l'héritage.

⏱ Lecture : 10 min · module complet 🎯 Très présent à l'examen (effets, portée, scan)
💡
À retenir : une définition = une règle (condition if + effet then). Une initiative = un paquet de règles. Une affectation = on applique la règle ou le paquet à une portée (groupe d'administration, abonnement, groupe de ressources). RBAC décide qui peut agir, Policy décide ce qui est permis.

Pour s'en souvenir : la conformité routière 🚛

C'est exactement ton nouveau poste de responsable sécurité et conformité, appliqué à Azure.

📘 Les règles

  • Définition = un article du règlement : « aucune remorque hors Canada »
  • Initiative = le cahier de conformité complet (heures de service, ronde de sécurité, poids…) qu'on applique d'un bloc
  • Affectation = « ce cahier s'applique à la division Québec » (et donc à tous ses camions, par héritage)
  • Exemption = une dérogation écrite pour un camion précis
  • RBAC = qui a le permis de conduire. Policy = le code de la route

🚨 Les effets

  • deny = la balance routière refuse le camion en surcharge : il ne passe pas
  • audit = le contrôleur note l'infraction au dossier, mais le camion repart
  • modify = on pose l'autocollant manquant au moment de l'inspection
  • deployIfNotExists = le camion n'a pas d'ELD ? on en installe un
  • denyAction = interdit de mettre au rancart (bloque la suppression)
  • manual = attestation signée par toi sur papier

1 · Pourquoi : la gouvernance du Cloud Adoption Framework

Le CAF est le guide Microsoft pour adopter le cloud. Sa méthode Gouverner tient en 5 étapes, et Azure Policy en est l'outil principal (étape 4).

  1. Créer une équipe de gouvernance qui définit et suit les règles
  2. Évaluer les risques : conformité, sécurité, opérations, coûts, données, ressources, IA
  3. Documenter les stratégies : ce qui est permis et ce qui ne l'est pas
  4. Appliquer les stratégies avec des outils automatiques (Azure Policy) et un contrôle humain
  5. Surveiller en continu. On répète les étapes 2 à 5

Exemples typiques : régions autorisées seulement, tailles de VM permises, étiquettes obligatoires, journaux de diagnostic envoyés à Log Analytics. Souveraineté : les secteurs régulés (gouvernement, finance, comme Desjardins) utilisent des initiatives toutes faites, par exemple le portfolio Microsoft for Sovereignty (dépôt GitHub Azure/industry-policy-portfolio).

2 · Comment une requête est évaluée

🌱 Greenfield (la règle d'abord)

La stratégie existe avant la ressource. Chaque création ou modification passe par RBAC puis par Policy. Pour une mise à jour, Policy fusionne le changement avec l'état actuel et évalue le résultat.

🏚️ Brownfield (les ressources d'abord)

On affecte une stratégie sur des ressources existantes. Elles sont marquées non conformes, jamais supprimées. Le scan tourne toutes les 24 h, ou à la demande avec az policy state trigger-scan. Durée imprévisible (basse priorité).

3 · Les 6 objets d'Azure Policy

ObjetCe qu'il fait
DéfinitionCondition + effet. Stockée dans un groupe d'administration ou un abonnement : cet endroit limite où on peut l'affecter. Intégrée (BuiltIn, Microsoft) ou personnalisée (Custom)
InitiativeAussi appelée policy set. Groupe de définitions affecté et géré comme une seule unité (ex. toutes les règles d'étiquetage)
AffectationApplique une définition ou une initiative à une portée. Options : étendues exclues, paramètres, message de non-conformité, sélecteurs de ressources (déploiement par vagues), overrides (changer l'effet sans toucher la définition), enforcementMode, identité managée (obligatoire pour deployIfNotExists et modify)
ExemptionRetire une ressource ou une portée de l'évaluation. Deux catégories : Mitigated (objectif atteint autrement) et Waiver (non-conformité acceptée temporairement)
AttestationPour l'effet manual : tu déclares toi-même l'état de conformité
CorrectionTâche de correction (remediation task) pour remettre en conformité les ressources existantes avec modify ou deployIfNotExists. Les nouvelles ressources sont corrigées automatiquement

4 · Anatomie d'une définition

📄 « Allowed locations » (intégrée)

{
  "displayName": "Allowed locations",
  "policyType": "BuiltIn",
  "mode": "Indexed",
  "parameters": {
    "listOfAllowedLocations": {
      "type": "Array",
      "metadata": { "strongType": "location" }
    }
  },
  "policyRule": {
    "if": {
      "allOf": [
        { "field": "location",
          "notIn": "[parameters('listOfAllowedLocations')]" },
        { "field": "location", "notEquals": "global" },
        { "field": "type",
          "notEquals": "Microsoft.AzureActiveDirectory/b2cDirectories" }
      ]
    },
    "then": { "effect": "deny" }
  }
}

🔍 Les morceaux à connaître

  • policyType : BuiltIn, Custom ou Static (conformité réglementaire Microsoft)
  • mode : All = tous les types de ressources. Indexed = seulement ceux qui ont des étiquettes et un emplacement (à utiliser pour les règles sur tags/location). Modes fournisseur : Microsoft.Kubernetes.Data, Microsoft.KeyVault.Data…
  • parameters : une seule définition réutilisable avec des valeurs différentes
  • policyRule : if (conditions) + then (effet)
  • Opérateurs logiques : allOf = ET, anyOf = OU, not = inverse
  • Conditions : field (propriété de la ressource), value, count. Critères : equals, like, in/notIn, contains, containsKey, exists, greater…
  • Fonctions propres à Policy : field(), utcNow(), addDays(), ipRangeContains(), current()

« global » est exclu car certains services mondiaux n'ont pas de région. Une fonction en erreur donne un deny.

5 · Les effets

EffetCe qu'il faitQuand
disabledDésactive la stratégie (vérifié en premier)synchrone

modifyAjoute, modifie ou retire des propriétés ou des étiquettes (ex. ajoute AppName=SpecialOrders si manquant)synchrone

Cumul : plusieurs stratégies sur une même ressource sont évaluées séparément, et la plus restrictive l'emporte. Un deny à n'importe quel niveau bloque.

6 · Évaluation et états de conformité

Déclencheurs

⚡ Quand ça évalue

  • Nouvelle affectation ou mise à jour
  • Création ou modification d'une ressource
  • Abonnement créé ou déplacé dans un groupe d'administration
  • Exemption créée, modifiée ou supprimée
  • Cycle de 24 h ou scan à la demande
États (priorité)

🚦 Du plus fort au plus faible

  • Non conforme
  • Conforme
  • Erreur
  • Conflit (deux affectations contradictoires)
  • Protégé (denyAction)
  • Exempté / Inconnu (manual)
Calcul

📊 Pourcentage

(conformes + exemptées + inconnues) ÷ total des ressources.

Tu veux réagir à un changement d'état ? Azure Policy publie des événements dans Event Grid (vers Functions, Logic Apps, webhook).

7 · Déployer une stratégie sans tout casser

🧪 enforcementMode

ModeJSONEffet appliquéJournal
ActivéDefault✅✅
DésactivéDoNotEnforce❌❌

C'est un « what if » : les ressources sont quand même évaluées et la conformité s'affiche, mais rien n'est bloqué. Différent de l'effet disabled, qui arrête toute évaluation. Les tâches de correction restent possibles.

🎯 Déploiement en anneaux

  1. Définition créée à la racine
  2. Affectation sur un petit anneau de test, enforcementMode désactivé
  3. Vérifier la conformité et la santé des applis
  4. Ajuster, puis réaffecter avec enforcementMode activé
  5. Revérifier, puis élargir anneau par anneau jusqu'à la production

🚛 Comme une nouvelle règle de flotte : on la teste sur 2 camions pilotes avant de l'imposer aux 200.

Bonne pratique : policy as code. Les définitions vivent dans Git, sont testées et déployées par pipeline (Azure DevOps ou GitHub Actions).

Pièges d'examen

🪤« J'affecte une stratégie "régions autorisées" : les ressources hors région sont supprimées. »Non. Elles sont seulement marquées non conformes. Seules les nouvelles créations hors région sont bloquées.
🪤« Pour empêcher quelqu'un de créer une VM, j'utilise Azure Policy. »Ça dépend. Empêcher une personne d'agir = RBAC. Empêcher tout le monde de créer une ressource non conforme = Policy.
🪤« Pour ajouter une étiquette manquante automatiquement, j'utilise audit. »Non, audit ne fait que signaler. Il faut modify (et une tâche de correction pour les ressources déjà là).
🪤« Une règle sur les étiquettes doit être en mode All. »Utilise Indexed : il ne regarde que les types qui supportent étiquettes et emplacement.
🪤« Je viens d'affecter la stratégie, elle s'applique tout de suite. »Jusqu'à 30 min de délai. Le scan des ressources existantes : toutes les 24 h, ou az policy state trigger-scan.
🪤« deployIfNotExists fonctionne sans rien configurer de plus. »L'affectation a besoin d'une identité managée avec les bons rôles pour déployer.
🪤« Une définition stockée dans l'abonnement A peut être affectée à l'abonnement B. »Non. Pour la réutiliser partout, stocke-la dans un groupe d'administration parent.

Mini-quiz

Encart Terraform

🟪 Affecter « Allowed locations » en mode test

data "azurerm_subscription" "current" {}

# Définition intégrée « Allowed locations » (par son nom d'affichage)
data "azurerm_policy_definition" "allowed_locations" {
  display_name = "Allowed locations"
}

resource "azurerm_subscription_policy_assignment" "canada_only" {
  name                 = "canada-only"
  subscription_id      = data.azurerm_subscription.current.id
  policy_definition_id = data.azurerm_policy_definition.allowed_locations.id
  enforce              = false   # = enforcementMode DoNotEnforce (what-if)

  parameters = jsonencode({
    listOfAllowedLocations = { value = ["canadacentral", "canadaeast"] }
  })

  non_compliance_message {
    content = "Seules les régions canadiennes sont permises."
  }
}

# Initiative perso : azurerm_policy_set_definition
# Exemption : azurerm_resource_group_policy_exemption (exemption_category = "Waiver" ou "Mitigated")
