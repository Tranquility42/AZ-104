Configurer la disponibilité des machines virtuelles

Maintenance et pannes, groupes à haute disponibilité (domaines d'erreur et de mise à jour), zones, mise à l'échelle verticale et horizontale, VMSS et mise à l'échelle automatique. Les notions marquées ➕ examen complètent le module.

⏱ Lecture : 9 min · module complet 🎯 FD/UD, zones vs groupes, SLA, VMSS : questions fréquentes
💡
À retenir : groupe à haute disponibilité = plusieurs racks d'un centre (FD contre les pannes, UD contre la maintenance, 5 UD par défaut, choisi à la création). Zones = plusieurs centres (99,99 %). Verticale = plus gros (redémarrage), horizontale = plus nombreux. VMSS + règles min / max / CPU = mise à l'échelle auto.

Pour s'en souvenir : la flotte de camions 🚛

🅿️ Où garer la flotte

  • Domaine d'erreur = une rangée du stationnement avec la même borne électrique : si la borne saute, toute la rangée est en panne
  • Domaine de mise à jour = un groupe d'entretien : on fait la vidange d'un groupe à la fois, jamais toute la flotte
  • Groupe à haute disponibilité = répartir les camions sur plusieurs rangées et groupes dans le même dépôt
  • Zones de disponibilité = 3 dépôts séparés dans la même ville : un incendie dans un dépôt n'arrête pas les autres

📈 Grossir la flotte

  • Verticale (scale up) = remplacer le porteur par un tracteur plus puissant : il faut l'arrêter, et il y a un modèle maximum
  • Horizontale (scale out) = ajouter des camions identiques : quasi sans limite
  • VMSS = un contrat de location de flotte : tous les camions sortent du même modèle
  • Mise à l'échelle auto = le répartiteur qui appelle des camions en renfort quand les commandes s'empilent et les renvoie le soir

2 · Groupes à haute disponibilité : domaines d'erreur et de mise à jour

Domaine d'erreur (FD)Domaine de mise à jour (UD)
Protège contreUne panne matérielle (courant, réseau, rack)Les redémarrages de maintenance planifiée
ImageUn rack physiqueUn groupe redémarré en même temps
Nombre➕ 2 par défaut, 3 max (selon la région)5 par défaut, de 1 à 20
RègleChaque VM est dans 1 FD et 1 UDUn seul UD redémarre à la fois ; le nombre d'UD ne change plus après création

📌 Règles du groupe à haute disponibilité

  • Une VM entre dans un groupe seulement à sa création. Pour changer : supprimer et recréer la VM.
  • Mêmes rôles et mêmes logiciels sur toutes les VM du groupe.
  • Un groupe par niveau d'appli (un pour le web, un pour SQL).
  • Combiner avec un Load Balancer et des disques managés.
  • Ne protège pas d'une erreur de l'OS ou de l'appli : il faut encore sauvegarde et reprise.

🏢 Zones de disponibilité

  • Des centres de données séparés dans une région, chacun avec courant, réseau et clim indépendants. Au moins 3 zones par région qui les supporte.
  • 3 VM dans 3 zones = réparties sur 3 FD et 3 UD.
  • Services zonaux : tu choisis la zone (VM, disques managés).
  • Services redondants entre zones : Azure réplique tout seul (stockage ZRS, Azure SQL Database).
  • IP publique Standard : zonale, redondante entre zones ou régionale.

5 · Mise à l'échelle automatique

  1. Limites : un minimum, un maximum et un nombre par défaut d'instances.
  2. Scale-out : seuil de CPU qui ajoute des instances, et combien en ajouter (pour une charge durable, pas un pic de 2 secondes).
  3. Scale-in : seuil de CPU qui en retire, et combien (le soir, le week-end).
  4. Durée de la requête : sur combien de minutes on fait la moyenne du CPU avant de décider.
  5. Planification (optionnel) : dates de début et de fin, jours qui se répètent.
➕ Toujours une règle de scale-out ET une règle de scale-in. Sans scale-in, la facture reste haute. Garde de l'écart entre les seuils (ex. 70 % / 30 %) pour éviter le yo-yo. Le temps de récupération (cooldown, 5 min par défaut) laisse les nouvelles VM démarrer avant de rejuger.

6 · ➕ En CLI

az vm availability-set create -g rg-labo -n as-web --platform-fault-domain-count 2 --platform-update-domain-count 5
az vm create -g rg-labo -n web1 --image Ubuntu2204 --availability-set as-web --generate-ssh-keys
az vm create -g rg-labo -n web-z1 --image Ubuntu2204 --zone 1 --generate-ssh-keys
az vmss create -g rg-labo -n vmss-web --image Ubuntu2204 --instance-count 2 \
  --orchestration-mode Flexible --zones 1 2 3 --generate-ssh-keys
az vmss scale -g rg-labo -n vmss-web --new-capacity 4
az monitor autoscale create -g rg-labo --resource vmss-web --resource-type Microsoft.Compute/virtualMachineScaleSets \
  -n auto-web --min-count 2 --max-count 5 --count 2
az monitor autoscale rule create -g rg-labo --autoscale-name auto-web \
  --condition "Percentage CPU > 70 avg 10m" --scale out 1
az monitor autoscale rule create -g rg-labo --autoscale-name auto-web \
  --condition "Percentage CPU < 30 avg 10m" --scale in 1

🚛 Appliquer à Optifuel

Ce que ça donne pour Optifuel :

  • Ton cluster k3s fait déjà de l'horizontal : plusieurs pods = plusieurs camions identiques.
  • En Azure, les nœuds k3s pourraient être un VMSS réparti sur 3 zones : une zone tombe, l'appli roule encore.
  • Les règles CPU 70 % / 30 %, c'est la même idée que le HPA de Kubernetes (CKA).

Pièges d'examen

🪤« J'ajoute ma VM existante au groupe à haute disponibilité. »Impossible : seulement à la création. Il faut recréer la VM.
🪤« Le groupe à haute disponibilité protège de la perte du centre de données. »Non, il reste dans un seul centre. Pour un centre entier : zones de disponibilité.
🪤« Je passe mon groupe de 5 à 10 domaines de mise à jour. »Le nombre d'UD est figé après création : supprimer et recréer le groupe.
🪤« Azure met à jour Windows dans mes VM pendant la maintenance planifiée. »Azure met à jour l'hôte. L'OS invité, c'est ta responsabilité.
🪤« Je passe le VMSS de Uniforme à Flexible. »Le mode d'orchestration se choisit à la création seulement.
🪤« Répartition fixe, région avec 3 FD : ça passe. »Fixe exige exactement 5 FD, sinon échec. Max s'adapte.
🪤« Monter à une plus grosse taille se fait sans coupure. »La mise à l'échelle verticale redémarre la VM. L'horizontale non.
🪤« J'ai mis une règle de scale-out, c'est suffisant. »Il faut aussi un scale-in, sinon tu paies le maximum pour toujours.

Encart Terraform

🟪 VMSS sur 3 zones + mise à l'échelle auto

resource "azurerm_linux_virtual_machine_scale_set" "web" {
  name                = "vmss-web"
  resource_group_name = azurerm_resource_group.labo.name
  location            = "eastus"
  sku                 = "Standard_B1s"
  instances           = 2
  zones               = ["1", "2", "3"]
  admin_username      = "azureuser"
  # admin_ssh_key, source_image_reference, os_disk,
  # network_interface { ... subnet_id ... } comme pour une VM
}
resource "azurerm_monitor_autoscale_setting" "web" {
  name                = "auto-web"
  resource_group_name = azurerm_resource_group.labo.name
  location            = "eastus"
  target_resource_id  = azurerm_linux_virtual_machine_scale_set.web.id
  profile {
    name = "defaut"
    capacity {
      default = 2
      minimum = 2
      maximum = 5
    }
    rule {
      metric_trigger {
        metric_name        = "Percentage CPU"
        metric_resource_id = azurerm_linux_virtual_machine_scale_set.web.id
        time_grain         = "PT1M"
        statistic          = "Average"
        time_window        = "PT10M"   # durée de la requête
        time_aggregation   = "Average"
        operator           = "GreaterThan"
        threshold          = 70
      }
      scale_action {
        direction = "Increase"
        type      = "ChangeCount"
        value     = "1"
        cooldown  = "PT5M"
      }
    }
    # + une règle "LessThan 30" / "Decrease" pour le scale-in
  }
}
