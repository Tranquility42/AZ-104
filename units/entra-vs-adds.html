Microsoft Entra ID vs AD DS

Deux annuaires Microsoft qui se ressemblent de nom, mais pas de nature : l'un vit dans tes serveurs et parle Kerberos, l'autre vit dans le cloud et parle HTTPS.

⏱ Lecture : 4 min 🎯 Domaine examen : Identités et gouvernance (20-25 %) 📚 Source : Microsoft Learn
💡
À retenir en une phrase : Entra ID n'est pas « AD DS dans le cloud ». AD DS est un annuaire hiérarchique pour un réseau local (Kerberos, LDAP, OU, GPO). Entra ID est un service d'identité plat et multilocataire pour les applications Internet (HTTPS, SAML, OpenID Connect, OAuth).

Pour s'en souvenir : la version camionnage 🚛

🏭 AD DS = la cour du terminal de ta compagnie

  • Une barrière avec un gardien qui connaît tout le monde : ça marche seulement sur place, dans le réseau de l'entreprise.
  • Le gardien te remet un billet d'entrée que tu montres à chaque quai : c'est Kerberos (des « tickets »).
  • Le plan de la cour découpé en zones (réparation, chargement, bureaux) : ce sont les OU (unités d'organisation).
  • Le règlement affiché par zone (vitesse 10 km/h, gilet obligatoire) : ce sont les GPO (objets de stratégie de groupe).
  • Les camions immatriculés au nom de la compagnie : ce sont les objets ordinateur joints au domaine.
  • L'annuaire téléphonique interne pour trouver le bon bureau : c'est DNS qui trouve les contrôleurs de domaine.

🛂 Entra ID = ton permis + ta carte EXPRESS/FAST

  • Reconnus partout sur la route, chez n'importe quel client, sans passer par la cour de la compagnie : c'est fait pour Internet (HTTPS 443).
  • Le permis prouve qui tu es : c'est l'authentification (OpenID Connect, SAML).
  • Le bon de livraison t'autorise à décharger au quai 7, et seulement là : c'est l'autorisation (OAuth).
  • La douane américaine accepte ta carte FAST canadienne sans refaire l'enquête : c'est la fédération (des tiers font confiance à Entra ID).
  • Pas de zones ni de règlement de cour : tous les chauffeurs sont sur une seule liste. Structure plate, ni OU ni GPO.

🧠 Et la VM Azure qui fait tourner AD DS ?

C'est comme louer une cour dans un autre terminal pour y garer ta flotte : c'est toujours ta cour, avec ton gardien et ton règlement. Tu n'es pas passé à la carte FAST pour autant. → Entra ID n'est pas utilisé.

Et on ne range pas la marchandise dans la cabine (le lecteur C:) : elle va dans la remorque (un disque de données). Pas d'entrepôt intermédiaire non plus : cache d'hôte = Aucune, l'écriture va directement sur le disque pour ne pas abîmer la base AD.

🏢 Exemple concret : ton futur employeur

Le matin, tu ouvres ta session sur un PC au bureau : AD DS vérifie ton mot de passe avec Kerberos, et une GPO installe le fond d'écran de l'entreprise. À midi, depuis ton téléphone, tu ouvres Outlook web ou le portail Azure : c'est Entra ID qui te connecte en HTTPS. Les deux sont souvent synchronisés (avec Entra Connect, on le verra plus tard), ce qui te permet d'utiliser le même mot de passe partout. Ce sont pourtant deux services différents.

Les deux fiches

🏢 AD DS sur site

Un composant de la suite Windows Active Directory, à côté de :

  • AD CS : services de certificats
  • AD LDS : annuaire léger
  • AD FS : fédération
  • AD RMS : gestion des droits

☁️ Entra ID cloud

  • Conçu pour les applications Internet
  • Multilocataire : chaque organisation a son locataire
  • Utilisateurs et groupes à plat
  • Services de fédération inclus : des tiers lui font confiance

Cas particulier : AD DS sur une VM Azure

⚠️ Ça n'a rien à voir avec Entra ID. Mettre un contrôleur de domaine sur une VM Azure, c'est juste déplacer ton AD DS local dans Azure pour gagner en scalabilité et disponibilité. Entra ID n'est absolument pas utilisé.
1Ajouter un ou plusieurs disques de données Azure
2Jamais le lecteur C: pour la base AD DS, les journaux et SYSVOL
3Préférence de cache d'hôte des disques : Aucune

Pièges d'examen

🪤« Entra ID, c'est AD DS hébergé dans le cloud. »Faux. Structure, protocoles et gestion sont différents. C'est un service d'identité, pas un contrôleur de domaine.
🪤« Je déploie un DC sur une VM Azure, donc j'utilise Entra ID. »Faux. C'est toujours ton AD DS. Entra ID n'intervient pas.
🪤« Une appli qui doit faire des requêtes LDAP peut viser Entra ID. »Non. Entra ID ne parle pas LDAP. Si l'énoncé exige LDAP ou Kerberos dans Azure sans gérer de DC, pense à Microsoft Entra Domain Services (service géré, voir unité 3).
🪤« OAuth sert à authentifier l'utilisateur. »Nuance. Dans le cours : SAML / WS-Fed / OIDC = authentification, OAuth = autorisation.
🪤« Je stocke la base NTDS sur C: avec le cache en lecture/écriture. »Faux. Disque de données séparé, cache d'hôte Aucune.

Mini-quiz

Encart Terraform

🟪 La même idée, en code

Les identités Entra se gèrent avec le provider azuread, les ressources Azure avec azurerm. Remarque : aucune ressource « OU » n'existe côté azuread, la structure est plate.

# Identité Entra ID : provider azuread
resource "azuread_user" "mah" {
  user_principal_name = "mah@contoso.onmicrosoft.com"
  display_name        = "Mah"
  password            = var.initial_password
}

resource "azuread_group" "ops" {
  display_name     = "ops"
  security_enabled = true
  members          = [azuread_user.mah.object_id]
}

# DC AD DS sur VM : disque de données, cache = None
resource "azurerm_virtual_machine_data_disk_attachment" "ntds" {
  managed_disk_id    = azurerm_managed_disk.ntds.id
  virtual_machine_id = azurerm_windows_virtual_machine.dc.id
  lun                = 0
  caching            = "None"  # ← le piège de la note
}

Unité 2 · Entra ID pour les applis cloud · l'essentiel

🚛
Analogie : plutôt que de tenir une liste de chauffeurs pour la carte carburant, une autre pour le dispatch et une autre pour l'ELD, la compagnie garde un seul dossier RH. Tu t'identifies une fois le matin et toutes les applis te reconnaissent.
1Un seul locataire pour Microsoft 365, Azure, Dynamics 365 et Intune, au lieu d'un locataire créé par chaque service.
2SSO : une connexion pour tout, y compris des applis tierces (Facebook, Google, Yahoo). Pour les devs, Entra peut s'appuyer sur d'autres IdP ou sur un AD DS local.
3Web App App Service : on active l'auth Entra dans le panneau Authentification, sans code. On désigne le locataire, et seuls ses comptes entrent.
4Réglages d'auth différents par emplacement de déploiement (slot staging vs production).
🪤« Il faut modifier le code pour protéger une Web App avec Entra ID. »Faux. Ça se fait dans le panneau Authentification du portail, et les réglages peuvent différer par slot.
🪤« Locataire = abonnement Azure. »Non (classique à l'examen). Le locataire, ce sont les identités. Un locataire peut avoir plusieurs abonnements, mais un abonnement fait confiance à un seul locataire.

🟪 Terraform

Le panneau Authentification correspond au bloc auth_settings_v2. Un slot (azurerm_linux_web_app_slot) a son propre bloc, d'où des réglages par slot.

resource "azurerm_linux_web_app" "app" {
  # …
  auth_settings_v2 {
    auth_enabled           = true
    require_authentication = true
    active_directory_v2 {
      client_id            = azuread_application.app.client_id
      tenant_auth_endpoint = "https://login.microsoftonline.com/${var.tenant_id}/v2.0"
    }
    login {}
  }
}
