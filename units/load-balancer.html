Azure Load Balancer

Répartir le trafic entrant entre plusieurs VM, éviter celles qui sont en panne, et savoir quand choisir un autre service (Application Gateway, Front Door, Traffic Manager). Les notions marquées ➕ examen ne sont pas dans le module mais tombent à l'examen.

⏱ Lecture : 7 min · module complet 🎯 Couche 4 vs couche 7 : question classique
💡
À retenir : Load Balancer travaille en couche 4 (IP, port, TCP/UDP) : il ne lit pas le contenu (URL, en-têtes). Il envoie le trafic d'une IP frontale vers un pool principal de VM selon des règles, et une sonde d'intégrité écarte les VM malades. Public = IP publique, face à Internet. Interne = IP privée, seulement dans le VNet (ou via VPN/ExpressRoute).

Pour s'en souvenir : le répartiteur au terminal 🚛

🏭 Le terminal

  • IP frontale = la barrière d'entrée du terminal : tous les camions arrivent au même endroit
  • Pool principal = les quais de chargement (les VM) derrière la barrière
  • Règle d'équilibrage = la consigne du répartiteur : « camions sur la porte 80 → quais 80 »
  • Sonde d'intégrité = le répartiteur qui appelle chaque quai toutes les 15 s : pas de réponse, plus de nouveaux camions
  • Couche 4 = il lit la plaque et la porte, jamais le contenu de la remorque

📋 Les options

  • Affinité de session = le même transporteur retourne toujours au même quai
  • Règle NAT entrante = une porte réservée au mécanicien pour aller à un quai précis (RDP sur une VM)
  • Règle de trafic sortant = le laissez-passer de sortie pour que les quais puissent envoyer des camions dehors (Internet)
  • Ports HA = « toutes les portes, tous les types de camions » : utile devant des postes de pesée (NVA)

1 · Le schéma : public et interne

C'est le scénario multiniveau du module (l'entreprise Adatum) : un LB public devant le niveau web, un LB interne entre le web et le traitement. Une VM écartée par la sonde garde ses connexions déjà ouvertes ; elle ne reçoit juste plus de nouvelles connexions.

2 · Les 7 composants

ComposantRôle
IP frontaleL'adresse que les clients appellent. Publique → LB public ; privée → LB interne. On peut en avoir plusieurs
Pool principalLes VM ou les instances d'un groupe de machines virtuelles identiques (VMSS) qui traitent les requêtes. Ajouter des VM = monter en charge ; le LB s'adapte tout seul
Règle d'équilibrageIP frontale + port → pool + port. Répartition par hachage à 5 tuples
Sonde d'intégritéTCP, HTTP ou HTTPS. Une VM malade ne reçoit plus de nouvelles connexions
Règle NAT entranteUne porte de l'IP frontale vers une VM précise (ex. RDP 3389 pour l'administration)
Ports HARègle « protocole : tous, port : 0 » sur un LB interne Standard : tous les ports TCP et UDP. Sert surtout devant des NVA
Règle de trafic sortantNAT source : les VM du pool sortent sur Internet avec l'IP publique du LB

3 · Comment il répartit

🔢 Hachage et affinité

Par défaut, le LB calcule un hachage à 5 tuples : IP source, port source, IP destination, port destination, protocole. Une même connexion reste sur la même VM, mais une nouvelle peut aller ailleurs.

Affinité de sessionMême VM tant que…
Aucune (défaut)la connexion dure (5 tuples)
IP client (2 tuples)même IP source + IP destination
IP client et protocole (3 tuples)même IP source + destination + protocole

🩺 Sondes d'intégrité

  • TCP : réussit si une session TCP s'ouvre sur le port
  • HTTP / HTTPS : réussit si la VM répond 200. Toutes les 15 s par défaut, délai d'attente 31 s
  • Réglables : port, URI (HTTP), intervalle, seuil de défaillance
  • Une sonde qui échoue ne coupe pas les connexions existantes
  • ➕ examen : avec un LB Standard, si toutes les sondes échouent, plus rien ne passe. Vérifie aussi que le NSG laisse passer la sonde (étiquette AzureLoadBalancer)

5 · Quand l'utiliser, et quoi d'autre

ServiceCouchePortéeChoisis-le si…
Load Balancer4 (TCP/UDP)RégionalLatence ultra-faible, tout protocole TCP/UDP, millions de flux, remplacement d'un LB matériel
Application Gateway7 (HTTP)RégionalRoutage par URL/chemin, terminaison TLS/SSL, pare-feu d'applications web (WAF)
Front Door7 (HTTP)MondialAppli web dans plusieurs régions : WAF, cache, basculement rapide
Traffic ManagerDNSMondialRépartir entre régions par DNS, tout protocole ; basculement plus lent (cache DNS, TTL)
✔ Oui

Niveau web exposé à Internet (LB public), trafic web → traitement (LB interne), RDP vers une VM précise (NAT entrante).

✖ Non

Une seule VM avec peu de trafic : pas besoin d'équilibrer.

✖ Non

Besoin de WAF ou de routage selon le contenu (URL) : Application Gateway ou Front Door.

6 · ➕ En CLI

az network public-ip create -g rg-labo -n pip-lb --sku Standard
az network lb create -g rg-labo -n lb-web --sku Standard \
  --public-ip-address pip-lb --frontend-ip-name fe-web --backend-pool-name pool-web
az network lb probe create -g rg-labo --lb-name lb-web -n sonde-http \
  --protocol Http --port 80 --path /
az network lb rule create -g rg-labo --lb-name lb-web -n regle-http \
  --protocol Tcp --frontend-port 80 --backend-port 80 \
  --frontend-ip-name fe-web --backend-pool-name pool-web --probe-name sonde-http
az network nic ip-config address-pool add -g rg-labo --nic-name nic-web1 \
  --ip-config-name ipconfig1 --lb-name lb-web --address-pool pool-web

💸 Un LB Standard est facturé à l'heure (quelques sous) plus les données : supprime le groupe après le test.

🚛 Appliquer à Optifuel

Tu en utilises déjà un sans le savoir.

  • Sur ton k3s, un Service de type LoadBalancer passe par ServiceLB, l'équilibreur intégré de k3s. Sur AKS, le même fichier crée automatiquement un Azure Load Balancer Standard avec son IP publique.
  • Devant Next.js, on met un contrôleur d'entrée (ingress) derrière ce LB. Ou une Application Gateway si tu veux un WAF devant les manifestes.
  • Donne à l'app une route /api/health qui répond 200 : c'est elle que la sonde appellera.
  • PostgreSQL n'a pas besoin de LB : avec le service géré, Azure s'occupe de la haute disponibilité.

Pièges d'examen

🪤« Je veux envoyer /images vers un pool et /api vers un autre : Load Balancer. »Routage par URL = couche 7 = Application Gateway.
🪤« Il me faut un WAF : j'ajoute un Load Balancer. »Le LB n'a pas de WAF : Application Gateway ou Front Door.
🪤« Mon appli tourne dans 3 régions : un Load Balancer public répartit entre elles. »Le LB est régional. Entre régions : Front Door (HTTP) ou Traffic Manager (DNS).
🪤« La sonde a échoué : les utilisateurs connectés sont coupés. »Non, seules les nouvelles connexions évitent la VM.
🪤« J'ai créé un LB Standard et rien ne passe : il est en panne. »Le Standard est fermé par défaut : il faut un NSG qui autorise le trafic.
🪤« Un utilisateur doit toujours tomber sur la même VM : je mets l'affinité Aucune. »Il faut l'affinité IP client (2 tuples) ou IP client et protocole (3 tuples).
🪤« Pour RDP sur une seule VM derrière le LB, j'ajoute une règle d'équilibrage 3389. »Ça répartirait entre toutes les VM : il faut une règle NAT entrante.

Encart Terraform

🟪 LB public : frontale, pool, sonde, règle

resource "azurerm_public_ip" "lb" {
  name                = "pip-lb"
  location            = "eastus"
  resource_group_name = azurerm_resource_group.labo.name
  allocation_method   = "Static"
  sku                 = "Standard"   # même SKU que le LB
}
resource "azurerm_lb" "web" {
  name                = "lb-web"
  location            = "eastus"
  resource_group_name = azurerm_resource_group.labo.name
  sku                 = "Standard"
  frontend_ip_configuration {
    name                 = "fe-web"
    public_ip_address_id = azurerm_public_ip.lb.id
  }
}
resource "azurerm_lb_backend_address_pool" "web" {
  name            = "pool-web"
  loadbalancer_id = azurerm_lb.web.id
}
resource "azurerm_lb_probe" "http" {
  name            = "sonde-http"
  loadbalancer_id = azurerm_lb.web.id
  protocol        = "Http"
  port            = 80
  request_path    = "/"
}
resource "azurerm_lb_rule" "http" {
  name                           = "regle-http"
  loadbalancer_id                = azurerm_lb.web.id
  protocol                       = "Tcp"
  frontend_port                  = 80
  backend_port                   = 80
  frontend_ip_configuration_name = "fe-web"
  backend_address_pool_ids       = [azurerm_lb_backend_address_pool.web.id]
  probe_id                       = azurerm_lb_probe.http.id
  load_distribution              = "Default"   # ou SourceIP (2 tuples), SourceIPProtocol (3)
}
# Brancher une VM : azurerm_network_interface_backend_address_pool_association
