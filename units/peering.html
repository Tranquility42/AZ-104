Configurer un peering de réseaux virtuels

Relier deux VNet en privé, partager une passerelle VPN, et contourner la règle du « pas de transit » avec un hub, des routes et une appliance. Les notions ajoutées pour l'examen sont marquées ➕ examen.

⏱ Lecture : 8 min · module complet 🎯 Non-transitivité et transit par passerelle : classiques d'examen
💡
À retenir : le peering relie deux VNet sans chevauchement d'adresses, en privé sur le réseau de Microsoft. Il est non transitif : A↔B et B↔C ne donnent pas A↔C. Il doit être Connecté des deux côtés. Un hub peut partager sa passerelle VPN avec ses rayons.

Pour s'en souvenir : les chemins privés entre terminaux 🚛

🛣️ Le peering

  • Peering = un chemin privé entre deux cours, sans sortir sur l'autoroute publique
  • Régional = deux terminaux de la même ville. Global = deux villes (Toronto ↔ Québec)
  • Initié / Connecté = la poignée de main : tant que les deux terminaux n'ont pas signé, la barrière reste fermée
  • Non transitif = un chemin Laval↔Montréal et Montréal↔Longueuil ne permet pas à un camion de Laval de traverser Montréal pour aller à Longueuil

🛃 Le hub

  • Hub and spoke = un terminal central relié à toutes les succursales
  • Transit par passerelle = le poste frontière (passerelle VPN vers le siège) est au terminal central : les succursales l'utilisent au lieu d'en construire chacune un
  • NVA = le répartiteur du terminal central qui redirige les camions d'une succursale à l'autre
  • UDR = les panneaux de détour : « pour Longueuil, passez par le répartiteur central »

1 · Topologie en étoile et non-transitivité

A et B n'ont pas de passerelle à eux : ils passent par celle du hub. Pour que A parle à B, deux options : un peering direct A↔B, ou faire passer le trafic par la NVA du hub avec des UDR (chaînage de services).

2 · Régional ou global, avantages et limites

🌍 Les deux types

  • Régional : VNet dans la même région
  • Global : VNet dans des régions différentes (pas entre régions Azure Government)
  • Fonctionne entre abonnements et même entre locataires différents
  • Chaque VNet reste une ressource séparée

✅ Avantages

  • Trafic privé sur le réseau de Microsoft : ni Internet, ni chiffrement, ni passerelle
  • Faible latence, grande bande passante
  • Aucune interruption des ressources pendant la création

⛔ Limites

  • Pas de chevauchement d'adresses, sinon la création échoue
  • Changer l'espace d'adresses : le module dit supprimer le peering, modifier, recréer. ➕ Aujourd'hui Azure permet de modifier puis resynchroniser le peering, mais retiens la réponse du module pour l'examen
  • Équilibreur de charge De base interne pas joignable en peering global : prendre Standard
  • La résolution DNS intégrée d'Azure ne traverse pas le peering : utiliser une zone DNS privée liée aux deux VNet
  • Une seule passerelle VPN par VNet
  • ➕ examen : le transfert de données en peering est facturé au Go, à l'entrée et à la sortie

3 · Créer le peering : les 4 réglages

Réglage (portail)Ce qu'il permetNom CLI
Trafic vers le réseau virtuel distantLaisser ce VNet communiquer avec l'autre (activé par défaut)--allow-vnet-access
Trafic transféré depuis le réseau distantAccepter du trafic qui ne vient pas directement de l'autre VNet (ex. relayé par une NVA)--allow-forwarded-traffic
Passerelle de réseau virtuel ou Route Server (côté hub)Autoriser le transit par passerelle : prêter sa passerelle VPN aux VNet appairés--allow-gateway-transit
Passerelle distante ou Route Server distant (côté rayon)Utiliser la passerelle distante du hub--use-remote-gateways

🖱️ Dans le portail

  1. Il faut le rôle Contributeur de réseau sur les deux VNet
  2. VNet 1 › Peerings › Ajouter
  3. Nommer les deux liens (ex. app-vnet-to-hub et hub-to-app-vnet), choisir le VNet distant, cocher les réglages
  4. Le portail crée les deux côtés d'un coup. Vérifier l'état : Connecté des deux côtés

🤝 Les états

  • Initié : un seul côté a été créé (fréquent en CLI ou PowerShell, où l'on crée chaque côté séparément)
  • Connecté : les deux côtés existent, le trafic passe
  • ➕ Déconnecté : l'autre côté a été supprimé. Il faut supprimer et recréer

Les NSG s'appliquent toujours : le peering ouvre la route, les NSG décident qui passe.

4 · Transit par passerelle

Côté hub

Contient la passerelle VPN (dans GatewaySubnet). Sur son peering : Autoriser le transit par passerelle.

Côté rayon

Sur son peering : Utiliser la passerelle distante. ➕ Impossible si le rayon a déjà sa propre passerelle.

Résultat

Les rayons atteignent le siège (VPN site à site), les clients point à site et d'autres VNet, avec une seule passerelle à payer. Marche en peering régional et global.

5 · Étendre le peering : UDR et chaînage de services

🧭 Les 4 mécanismes

  • Hub and spoke : les rayons sont appairés au hub, qui héberge NVA et passerelle
  • UDR (route définie par l'utilisateur) : le prochain saut peut être l'IP d'une VM du VNet appairé ou une passerelle VPN
  • Chaînage de services : des UDR qui envoient le trafic vers une appliance ou une passerelle d'un VNet appairé
  • Azure Virtual Network Manager : crée automatiquement les peerings en étoile ou en maillage, à grande échelle

➕ examen : faire passer A→B par la NVA

  1. Peering A↔hub et B↔hub, avec Trafic transféré autorisé
  2. Sur la carte réseau de la NVA : activer le transfert IP
  3. Table de routage sur le sous-réseau de A : destination 10.2.0.0/16, prochain saut Appliance virtuelle 10.0.1.4
  4. Même chose côté B vers 10.1.0.0/16

6 · Les commandes

# Un côté du peering (à refaire dans l'autre sens)
az network vnet peering create -g rg-labo -n app-to-hub \
  --vnet-name app-vnet --remote-vnet hub-vnet \
  --allow-vnet-access --allow-forwarded-traffic --use-remote-gateways

az network vnet peering list -g rg-labo --vnet-name app-vnet -o table   # voir l'état

# Route vers la NVA (chaînage de services)
az network route-table create -g rg-labo -n rt-app
az network route-table route create -g rg-labo --route-table-name rt-app -n vers-dev \
  --address-prefix 10.2.0.0/16 --next-hop-type VirtualAppliance --next-hop-ip-address 10.0.1.4
az network vnet subnet update -g rg-labo --vnet-name app-vnet -n frontend --route-table rt-app

# Tester la connexion depuis une VM Windows (exercice)
Test-NetConnection -ComputerName 10.2.0.4 -Port 3389

PowerShell : Add-AzVirtualNetworkPeering -Name app-to-hub -VirtualNetwork $app -RemoteVirtualNetworkId $hub.Id, Get-AzVirtualNetworkPeering. Dans l'exercice, Network Watcher › Résolution des problèmes de connexion teste aussi le lien entre deux VM. 💸 Le peering est presque gratuit pour un labo, ce sont les VM qui coûtent : supprime le groupe de ressources après.

Pièges d'examen

🪤« A est appairé à B, B à C : A peut joindre C. »Non, le peering est non transitif. Il faut A↔C, ou une NVA dans B avec des UDR.
🪤« J'ai créé le peering depuis app-vnet, c'est bon, il est Initié. »Pas encore. Il doit être Connecté des deux côtés.
🪤« Chaque rayon a besoin de sa passerelle VPN pour joindre le siège. »Non : Autoriser le transit par passerelle sur le hub + Utiliser la passerelle distante sur le rayon.
🪤« J'appaire 10.0.0.0/16 avec 10.0.0.0/24. »Échec : les espaces se chevauchent.
🪤« Après le peering, mes VM se trouvent par leur nom dans l'autre VNet. »La résolution DNS intégrée ne traverse pas le peering : zone DNS privée liée aux deux VNet.
🪤« Le peering global passe par Internet, il faut chiffrer. »Non, il reste sur le réseau dorsal de Microsoft, privé.

🟪 Les deux côtés du peering hub ↔ rayon

resource "azurerm_virtual_network_peering" "hub_to_app" {
  name                      = "hub-to-app"
  resource_group_name       = azurerm_resource_group.labo.name
  virtual_network_name      = azurerm_virtual_network.hub.name
  remote_virtual_network_id = azurerm_virtual_network.app.id
  allow_forwarded_traffic   = true
  allow_gateway_transit     = true    # le hub prête sa passerelle
}

resource "azurerm_virtual_network_peering" "app_to_hub" {
  name                      = "app-to-hub"
  resource_group_name       = azurerm_resource_group.labo.name
  virtual_network_name      = azurerm_virtual_network.app.name
  remote_virtual_network_id = azurerm_virtual_network.hub.id
  allow_forwarded_traffic   = true
  use_remote_gateways       = true    # le rayon utilise celle du hub
}

# UDR vers la NVA du hub
resource "azurerm_route_table" "app" {
  name                = "rt-app"
  location            = "canadacentral"
  resource_group_name = azurerm_resource_group.labo.name
  route {
    name                   = "vers-dev"
    address_prefix         = "10.2.0.0/16"
    next_hop_type          = "VirtualAppliance"
    next_hop_in_ip_address = "10.0.1.4"
  }
}
