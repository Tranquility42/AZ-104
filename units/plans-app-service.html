Configurer des plans Azure App Service

Ce qu'est un plan, les niveaux tarifaires et leurs limites, scale up et scale out, mise à l'échelle automatique par règles ou élastique. Les notions marquées ➕ examen complètent le module.

⏱ Lecture : 6 min · module complet 🎯 Quel niveau pour quelle fonction : questions fréquentes
💡
À retenir : le plan = les VM qui font tourner tes applis ; toutes ses applis partagent toutes ses instances. Free/Shared : partagé, pas de SLA. Basic : dédié, 3 instances, manuel. Standard : auto + 5 emplacements. Premium : 30 instances, 20 emplacements, élastique. Isolated v2 : réseau dédié, 200 instances.

Pour s'en souvenir : le terminal loué 🚛

🏭 Le plan = le terminal

  • Plan App Service = le terminal que tu loues (des quais, des employés) ; les applis sont les clients qui s'y installent
  • Toutes les applis du plan partagent les mêmes quais : un client trop gros ralentit tout le monde
  • Tu paies le terminal, pas chaque client : 3 applis dans un plan = un seul loyer

📈 Grossir

  • Scale up = passer à un terminal de catégorie supérieure (plus grands quais, et des services en plus : domaine perso, TLS, emplacements…)
  • Scale out = ouvrir plus de quais identiques ; chaque appli tourne sur tous les quais
  • Pas besoin de toucher le code : le changement prend quelques secondes

1 · Ce que définit un plan

RéglageÀ retenir
OSLinux ou Windows : choisi à la création, il limite les niveaux tarifaires disponibles
RégionLes VM du plan sont créées dans cette région ; une appli d'une autre région = un autre plan
Niveau tarifaireFonctionnalités et prix
Nombre d'instancesCombien de VM ; toutes les applis du plan tournent sur toutes les instances
Taille d'instanceCPU, mémoire, stockage
Isoler une appli dans son propre plan si elle consomme beaucoup, si elle doit grossir indépendamment des autres, ou si elle doit tourner dans une autre région. Sinon, regrouper les applis économise de l'argent, mais attention à ne pas surcharger le plan.

Basic et Standard ont un équilibrage de charge intégré entre les instances. Premium v3 (séries Dav4/Ddv4, SSD, tailles optimisées mémoire) et Isolated v2 sont recommandés pour les nouveaux déploiements. ➕ Le niveau Shared (D1) accepte déjà un domaine personnalisé, mais pas de certificat TLS. Le module cite aussi « jusqu'à 100 instances » pour l'ancien Isolated ; retiens 200 pour Isolated v2.

3 · Scale up et scale out

Scale up (vertical)Scale out (horizontal)
CommentChanger de niveau tarifaire (ou de taille)Ajouter des instances, manuellement ou en auto
DonnePlus de CPU, mémoire, disque et des fonctionnalités : VM dédiées, domaine perso, TLS, emplacements, mise à l'échelle autoPlus de capacité, jusqu'au max du niveau
EffetToutes les applis du plan, en quelques secondes, sans redéploiementIdem

🏨 L'exemple de l'hôtel du module

  1. Free pendant les tests.
  2. Il faut un nom de domaine perso → Shared.
  3. Il faut une liaison TLS/SSL → Basic.
  4. Il faut des environnements de préproduction (emplacements) → Standard.
  5. Il faut plus de cœurs ou de mémoire → une plus grosse taille dans le même niveau.
⚠️ Le plan ne gère que ses VM. Une base Azure SQL ou un compte de stockage utilisés par l'appli se mettent à l'échelle séparément.

4 · La mise à l'échelle automatique

📏 Basée sur des règles (Standard et +)

  • Paramètre de mise à l'échelle → regroupé en profils → contenant des règles
  • Règle = déclencheur + action (ajouter ou retirer)
  • Déclencheur métrique : temps CPU, temps de réponse moyen, requêtes (« CPU > 50 % »)
  • Déclencheur horaire : « tous les samedis à 8 h »
  • Notifications : courriels et/ou webhooks

⚡ Élastique (Premium v2 / v3 seulement)

  • Basée sur le trafic HTTP, aucune règle à écrire
  • C'est la plateforme qui décide
  • Instances toujours prêtes (déjà chaudes) pour absorber les pics
  • Pour une charge imprévisible et moins de gestion
Bonne pratiquePourquoi
Minimum d'instancesL'appli tourne même sans charge
Maximum d'instancesPlafonne la facture horaire
Assez d'écart entre min et maxSinon la mise à l'échelle n'a pas de marge
Toujours scale-out + scale-inSans scale-out : appli lente ; sans scale-in : facture haute
Bonne statistique (moyenne, min, max, total)La moyenne évite de réagir à un pic isolé
Nombre par défaut raisonnableUtilisé quand les métriques ne sont pas disponibles
Activer les notificationsSavoir quand ça grossit

5 · ➕ En CLI

az appservice plan create -g rg-labo -n plan-web --sku B1 --is-linux -l eastus
az appservice plan update -g rg-labo -n plan-web --sku S1          # scale up
az appservice plan update -g rg-labo -n plan-web --number-of-workers 3   # scale out
az appservice plan list -o table

🚛 Appliquer à Optifuel

Si Optifuel passait sur App Service :

  • Dev : B1 Linux (pas cher, mais pas d'emplacements).
  • Prod : S1 minimum pour la mise à l'échelle auto et un emplacement staging.
  • PostgreSQL reste à part (Azure Database for PostgreSQL) : il se met à l'échelle séparément du plan.

Pièges d'examen

🪤« Je paie chaque appli de mon plan Standard. »Calcul dédié : tu paies le plan (ses instances). La facturation par appli, c'est Free/Shared.
🪤« Je mets la mise à l'échelle auto sur mon plan Basic. »Basic = manuel (3 instances max). Mise à l'échelle auto à partir de Standard.
🪤« Je veux des emplacements de déploiement en Basic. »Emplacements à partir de Standard (5), Premium (20).
🪤« Plan Free avec SLA pour un petit client. »Free et Shared : aucun SLA, dev/test seulement.
🪤« Scale out d'une seule appli du plan. »Le scale out s'applique à toutes les applis du plan. Pour isoler : un plan séparé.
🪤« La mise à l'échelle élastique est dispo en Standard. »Élastique = Premium v2/v3 seulement.
🪤« En montant le plan, ma base Azure SQL grossit aussi. »Les autres services se mettent à l'échelle séparément.

}
