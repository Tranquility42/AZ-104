Sécuriser l'accès avec Azure RBAC

Qui peut faire quoi, et où, sur tes ressources Azure. Le module est court, mais RBAC revient partout à l'examen : j'ai ajouté les notions qui y tombent souvent (marquées ➕ examen).

⏱ Lecture : 8 min · module complet 🎯 Incontournable AZ-104
💡
À retenir : une attribution de rôle = QUI (principal de sécurité) + QUOI (définition de rôle) + OÙ (étendue). Accorder un accès = créer une attribution. Retirer un accès = la supprimer. Les rôles s'additionnent et descendent par héritage.

Pour s'en souvenir : le coffre à clés du terminal 🔑

🚛 Les rôles = les trousseaux

  • Propriétaire = la clé maîtresse + le droit de faire des doubles pour les autres
  • Contributeur = les clés de tous les camions, mais interdit de faire des doubles
  • Lecteur = il peut regarder le tableau de répartition, sans toucher à rien
  • Administrateur de l'accès utilisateur = le gardien du coffre à clés : il fait les doubles, mais ne conduit pas
  • Contributeur de machines virtuelles = les clés des tracteurs seulement, pas des remorques

📒 Le registre des clés

  • Principal = le chauffeur (ou une équipe, ou un système automatique)
  • Étendue = toute la division, un terminal, une remorque ou un camion
  • Attribution = la ligne signée dans le registre : « Alain, clés des tracteurs, terminal Laval »
  • Héritage = une clé du terminal ouvre aussi tous les camions du terminal
  • Journal d'activité = le registre qu'on sort pour l'audit trimestriel

1 · Qui + Quoi + Où = attribution

Les 4 rôles fondamentaux

RôleVoirCréer / modifierDonner l'accès
Propriétaire (Owner)✔✔✔
Contributeur (Contributor)✔✔✘
Lecteur (Reader)✔✘✘
Administrateur de l'accès utilisateur✔✘✔

Il existe des centaines de rôles intégrés spécialisés (Contributeur de machines virtuelles, Opérateur de sauvegarde, Contributeur de réseau…). Le principe du moindre privilège : choisir le plus petit rôle, sur la plus petite étendue.

2 · Étendue et héritage

  1. Groupe d'administration : plusieurs abonnements
  2. Abonnement : tous ses groupes de ressources
  3. Groupe de ressources : toutes ses ressources
  4. Ressource : une seule VM, un seul compte de stockage…

🔽 Ça descend, ça s'additionne

  • Contributeur sur l'abonnement = Contributeur sur tous ses groupes et ressources
  • Dans l'onglet Attributions de rôles, l'origine est indiquée : Cette ressource ou (Hérité)
  • Lecteur + Contributeur sur le même groupe = tu as les deux (lecture et écriture)
  • On ne peut pas retirer à un niveau enfant un droit hérité d'un parent. Il faut supprimer l'attribution là où elle a été faite
Entra ID d'abord : chaque abonnement fait confiance à un seul locataire Entra. Les utilisateurs, groupes et applis de ce locataire sont ceux à qui tu peux donner des rôles. Désactiver un compte (même synchronisé depuis AD local avec Entra Connect) lui retire l'accès partout.

3 · Dans une définition de rôle

📄 Le rôle Contributeur (simplifié)

{
  "Name": "Contributor",
  "Actions": [ "*" ],
  "NotActions": [
    "Microsoft.Authorization/*/Delete",
    "Microsoft.Authorization/*/Write",
    "Microsoft.Authorization/elevateAccess/Action",
    "Microsoft.Blueprint/blueprintAssignments/write",
    "Microsoft.Blueprint/blueprintAssignments/delete"
  ],
  "DataActions": [],
  "NotDataActions": [],
  "AssignableScopes": [ "/" ]
}

🧮 Le calcul

Droits effectifs = Actions − NotActions

  • * = toutes les opérations du plan de contrôle
  • Les NotActions retirent Microsoft.Authorization/* en écriture et suppression : c'est pour ça que le Contributeur ne peut pas donner d'accès
  • ➕ examen : DataActions = opérations sur les données (lire un blob, un secret). Contributeur ne lit pas les blobs par Entra : il faut un rôle de données comme Lecteur des données Blob du stockage
  • ➕ examen : AssignableScopes = où un rôle personnalisé peut être attribué
  • ➕ examen : NotActions n'est pas un refus. Si un autre rôle donne l'action, tu l'as. Seule une attribution de refus (deny assignment) bloque, et tu ne peux pas en créer toi-même (Azure les pose, par exemple via les Blueprints ou les applis managées)

4 · Dans le portail (les 3 exercices)

Lister

👀 Voir les accès

  • Tes droits : menu du profil › … › Mes autorisations
  • Une ressource : Contrôle d'accès (IAM) › onglet Attributions de rôles
  • Onglet Rôles › Afficher › Attributions pour voir qui a ce rôle
  • Vérifier l'accès : chercher un utilisateur et voir ses rôles ici
Accorder

➕ Donner un rôle

  • Il faut être Propriétaire ou Admin de l'accès utilisateur (sinon le bouton est grisé)
  • IAM › Ajouter › Ajouter une attribution de rôle
  • Onglet Rôle (ex. Contributeur de machines virtuelles) › Membres › Vérifier + attribuer
  • Retirer : cocher l'attribution › Supprimer
Auditer

📜 Journal d'activité

  • Journal d'activité › Période : Le mois dernier
  • Filtre Opération : tape role
  • Create / Delete role assignment, Create or update / Delete custom role definition
  • Export CSV pour l'audit

🧪 Gratuit à pratiquer : donner et retirer des rôles ne coûte rien. Essaie sur ton groupe de ressources avec labadmin comme membre.

5 · ➕ examen : rôles Azure ≠ rôles Entra ≠ Policy

Un Administrateur général Entra n'a pas automatiquement accès aux ressources Azure. Il peut élever son accès (Entra ID › Propriétés › « Gestion de l'accès pour les ressources Azure ») pour devenir Admin de l'accès utilisateur à la racine.

Pièges d'examen

🪤« Alain est Contributeur sur l'abonnement, il peut donc donner l'accès à son collègue. »Non. Contributeur ne peut pas attribuer de rôles. Il faut Propriétaire ou Admin de l'accès utilisateur.
🪤« Pour qu'un auditeur voie tout sans rien changer, je lui donne Contributeur. »Lecteur suffit (moindre privilège).
🪤« Je retire à Alain le droit d'un groupe de ressources alors qu'il est Contributeur sur l'abonnement. »Impossible au niveau du groupe : l'héritage gagne. Supprime l'attribution sur l'abonnement et refais-la plus bas.
🪤« Un administrateur général Entra gère forcément toutes les VM. »Faux. Rôles Entra et rôles Azure sont séparés. Il doit élever son accès d'abord.
🪤« Contributeur peut lire le contenu d'un blob avec son compte Entra. »Non, c'est du plan de données : il faut Lecteur des données Blob du stockage (DataActions).
🪤« Pour voir qui a donné un rôle le mois dernier, je regarde l'onglet IAM. »IAM montre l'état actuel. L'historique est dans le Journal d'activité (filtre Opération « role »).

Mini-quiz

Encart Terraform

🟪 Une attribution de rôle en code

data "azuread_user" "alain" {
  user_principal_name = "alain@bewithulive.onmicrosoft.com"
}

resource "azurerm_resource_group" "labo" {
  name     = "rg-labo-rbac"
  location = "canadacentral"
}

# QUI + QUOI + OÙ
resource "azurerm_role_assignment" "alain_vm" {
  principal_id         = data.azuread_user.alain.object_id     # qui
  role_definition_name = "Virtual Machine Contributor"        # quoi
  scope                = azurerm_resource_group.labo.id          # où
}

# Rôle personnalisé : azurerm_role_definition (permissions { actions, not_actions }, assignable_scopes)
