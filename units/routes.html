Contrôler le trafic avec des routes

Comment Azure décide où envoyer chaque paquet, et comment forcer le trafic à passer par une appliance de sécurité (NVA) avec des routes personnalisées. Les notions marquées ➕ examen complètent les unités théoriques.

⏱ Lecture : 8 min · module complet 🎯 Prochain saut et préfixe le plus long : questions fréquentes
💡
À retenir : Azure crée des routes système automatiques. Tu peux les remplacer par des routes définies par l'utilisateur (UDR) dans une table de routage associée à un sous-réseau. Azure choisit la route au préfixe le plus long (le plus précis). Pour une NVA : prochain saut Appliance virtuelle + transfert IP activé sur sa carte réseau et dans son système.

Pour s'en souvenir : la répartition et la balance routière 🚛

🗺️ Les routes

  • Routes système = le GPS par défaut : il connaît les rues du terminal et la sortie vers l'autoroute
  • Table de routage = la feuille de route affichée à la sortie d'une zone (sous-réseau)
  • UDR = la consigne du répartiteur : « pour aller à l'entrepôt privé, passe d'abord par la balance »
  • Préfixe le plus long = la consigne la plus précise gagne : « quai 12 » bat « Montréal »
  • Prochain saut « Aucun » = route barrée : le camion est refusé

⚖️ La NVA

  • NVA = la balance routière / poste d'inspection installé dans la DMZ
  • Transfert IP = l'inspecteur a le droit de laisser repartir un camion qui ne lui était pas destiné. Sans ça, il le garde et la livraison n'arrive jamais
  • Il faut le permis à deux endroits : sur la carte réseau (Azure) et dans le système de la VM (Linux)
  • traceroute = le carnet de route qui liste chaque arrêt du trajet

1 · Le scénario de l'exercice

Le traceroute de public vers private montre deux sauts : 10.0.2.4 (la NVA) puis 10.0.1.4. Dans l'autre sens, un seul : la route ne s'applique qu'au trafic qui sort du sous-réseau associé.

3 · Les routes personnalisées (UDR)

🎯 Types de prochain saut

TypePour
Appliance virtuelleEnvoyer vers une NVA : il faut donner son IP
Passerelle de réseau virtuelEnvoyer vers la passerelle VPN
Réseau virtuelGarder dans le VNet
InternetSortir vers Internet
AucunBloquer (abandonner le trafic)

📏 Règles

  • Une table de routage est associée à 0 ou plusieurs sous-réseaux, et un sous-réseau a au maximum une table
  • La table doit être dans la même région et le même abonnement que le VNet
  • Elle agit sur le trafic qui sort du sous-réseau
  • Choix de la route : le préfixe le plus long gagne (un /24 bat un /16)
  • À préfixe égal : UDR > BGP > système
  • BGP : routes apprises de ton réseau local via VPN ou ExpressRoute. L'option Propager les routes de passerelle de la table (--disable-bgp-route-propagation false) les accepte ou non
  • Tunneling forcé : UDR 0.0.0.0/0 → NVA ou passerelle pour inspecter toute la sortie Internet

4 · Les appliances virtuelles réseau (NVA)

C'est quoi

Une VM qui fait pare-feu, filtrage, inspection de paquets, optimisation WAN ou routage. Souvent une image du Marketplace (Palo Alto, Fortinet, Check Point…), ici un simple Ubuntu.

Où

Dans un sous-réseau DMZ (périmètre) entre la zone publique et la zone privée, ou dans le hub d'une topologie en étoile.

Haute dispo

Une seule NVA = point de défaillance unique. En production : deux NVA ou plus derrière un équilibreur de charge. Alternative gérée : Azure Firewall.

Le double transfert IP : sur la carte réseau Azure (az network nic update --ip-forwarding true), sinon Azure jette les paquets qui ne sont pas destinés à la VM. Et dans le système (sudo sysctl -w net.ipv4.ip_forward=1), sinon Linux les jette. ➕ Cette commande sysctl ne survit pas à un redémarrage : en vrai, on l'écrit dans /etc/sysctl.conf.

5 · Les étapes de l'exercice

  1. Créer la table publictable et la route productionsubnet : 10.0.1.0/24 → Appliance virtuelle 10.0.2.4
  2. Créer le VNet et les 3 sous-réseaux (public, private, dmz)
  3. Associer publictable à publicsubnet
  4. Créer la VM nva dans dmzsubnet (elle reçoit 10.0.2.4, la première adresse libre)
  5. Activer le transfert IP sur sa carte réseau, puis dans Linux
  6. Créer les VM public et private avec cloud-init (installe traceroute)
  7. Tester avec traceroute dans les deux sens
az network route-table create -g rg-labo -n publictable --disable-bgp-route-propagation false

az network route-table route create -g rg-labo --route-table-name publictable \
  -n productionsubnet --address-prefix 10.0.1.0/24 \
  --next-hop-type VirtualAppliance --next-hop-ip-address 10.0.2.4

az network vnet subnet update -g rg-labo --vnet-name vnet -n publicsubnet --route-table publictable

az network nic update -g rg-labo -n <nom-carte-nva> --ip-forwarding true
ssh azureuser@<ip-publique-nva> 'sudo sysctl -w net.ipv4.ip_forward=1'

ssh azureuser@<ip-publique-vm-public> 'traceroute private --type=icmp'
az network nic show-effective-route-table -g rg-labo -n <nom-carte> -o table   # ➕ routes effectives

💸 3 VM Ubuntu : supprime le groupe de ressources dès la fin du test. 🔍 Pour vérifier quelle route s'applique : carte réseau › Routes effectives dans le portail, ou Network Watcher › Prochain tronçon.

🚛 Appliquer à Optifuel

Honnêtement : pas nécessaire pour Optifuel au début.

  • Les routes système suffisent pour un seul VNet : rien à configurer.
  • Une route définie par l'utilisateur (0.0.0.0/0 → pare-feu) devient utile si l'employeur exige que toute sortie Internet passe par un pare-feu inspecté.
  • Azure Firewall coûte environ 1,25 $ US de l’heure : à tester une heure puis destroy, pas à laisser tourner sur ton crédit.

Pièges d'examen

🪤« J'ai mis la route vers la NVA, mais le trafic n'arrive pas : la route est mauvaise. »Vérifie le transfert IP sur la carte réseau de la NVA (et dans son OS).
🪤« Une route 10.0.0.0/16 → Internet et une 10.0.1.0/24 → NVA : le trafic vers 10.0.1.5 sort sur Internet. »Non, le /24 est plus précis : il va à la NVA.
🪤« J'associe la table de routage au VNet. »On l'associe à des sous-réseaux, pas au VNet.
🪤« Pour bloquer le trafic vers un réseau, je mets le prochain saut Internet. »Prochain saut Aucun = abandon du trafic.
🪤« Ma route sur publicsubnet fait aussi passer le retour privé → public par la NVA. »Non, elle ne vise que le trafic qui sort de publicsubnet. Pour un trajet symétrique, il faut aussi une table sur privatesubnet.
🪤« Prochain saut Appliance virtuelle, sans adresse IP. »L'IP de la NVA est obligatoire pour ce type.

🟪 Table de routage + NVA avec transfert IP

resource "azurerm_route_table" "public" {
  name                = "publictable"
  location            = "canadacentral"
  resource_group_name = azurerm_resource_group.labo.name

  route {
    name                   = "productionsubnet"
    address_prefix         = "10.0.1.0/24"
    next_hop_type          = "VirtualAppliance"
    next_hop_in_ip_address = "10.0.2.4"
  }
}

resource "azurerm_subnet_route_table_association" "public" {
  subnet_id      = azurerm_subnet.public.id
  route_table_id = azurerm_route_table.public.id
}

resource "azurerm_network_interface" "nva" {
  name                  = "nic-nva"
  location              = "canadacentral"
  resource_group_name   = azurerm_resource_group.labo.name
  ip_forwarding_enabled = true   # transfert IP côté Azure
  ip_configuration {
    name                          = "ipconfig1"
    subnet_id                     = azurerm_subnet.dmz.id
    private_ip_address_allocation = "Static"
    private_ip_address            = "10.0.2.4"
  }
}
# Côté Linux : custom_data (cloud-init) avec net.ipv4.ip_forward=1
