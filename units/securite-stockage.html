Sécuriser le Stockage Azure

Les façons d'autoriser l'accès, les signatures d'accès partagé (SAS) et leur URI, le chiffrement et les clés gérées par le client, la surveillance. Les notions marquées ➕ examen complètent le module.

⏱ Lecture : 8 min · module complet 🎯 Lire une URI SAS : question classique
💡
À retenir : préfère Entra ID + RBAC (identités managées) à la clé du compte. Une SAS donne un accès limité et daté ; la plus sûre est la délégation d'utilisateur. Une stratégie d'accès stockée permet de révoquer des SAS sans changer les clés. Tout est chiffré au repos (AES 256) ; la clé gérée par le client vit dans Key Vault.

Pour s'en souvenir : les clés de l'entrepôt 🚛

🔑 Qui entre

  • Clé d'accès du compte = le passe-partout du propriétaire : ouvre tout, pour toujours. On ne le prête jamais
  • SAS = le laissez-passer daté remis au transporteur : « remorque 12, lecture seule, de 8 h à 10 h, depuis ton IP »
  • Stratégie d'accès stockée = le registre au poste de garde : on raye une ligne et tous les laissez-passer liés sont annulés
  • Entra ID + RBAC = la carte d'employé nominative : le meilleur choix

🔐 Comment c'est protégé

  • Chiffrement au repos = toutes les remorques sont verrouillées d'office (AES 256), sans frais
  • Clé gérée par Microsoft = Microsoft garde le cadenas et sa clé
  • Clé gérée par le client = ton propre cadenas, rangé dans ton coffre (Key Vault) : tu peux le changer ou le retirer
  • Defender for Storage = le chien renifleur qui fouille les palettes entrantes (logiciels malveillants)

2 · Les signatures d'accès partagé (SAS)

Type de SASSigné avecPortée
Délégation d'utilisateurIdentifiants Entra IDBlob et Data Lake seulement. Le plus sûr
ServiceClé du compteUn service (Blob, Files, Queue ou Table) et des ressources précises
CompteClé du compteUn ou plusieurs services, plus des opérations de niveau service (ex. créer des systèmes de fichiers)
Stratégie d'accès stockée : définie sur le conteneur (ou la file, la table, le partage) ; une SAS de service y fait référence. Avantage : on révoque ou modifie toutes les SAS liées sans régénérer les clés du compte. Sans elle, la seule façon d'annuler une SAS volée est de régénérer la clé qui l'a signée.

✅ Bonnes pratiques SAS

  • Toujours HTTPS (sinon interception)
  • Expiration courte, et le client renouvelle avant la fin
  • Heure de début 15 minutes dans le passé (ou aucune) : les horloges diffèrent
  • Permissions minimales : lecture seule si c'est assez
  • Préférer une stratégie d'accès stockée
  • Valider les données écrites avec une SAS avant de les utiliser

🤔 Pas toujours la bonne idée

  • Opération risquée : passer par un service intermédiaire qui vérifie, journalise, puis écrit
  • Tous les blobs d'un conteneur doivent être publics ? Mets le conteneur public plutôt que distribuer des SAS
  • Dans ton code : identité managée plutôt que SAS

➕ Lettres de sp à reconnaître : r read · w write · d delete · l list · a add · c create. ➕ ss : b blob · f file · q queue · t table. ➕ srt (SAS de compte) : s service · c conteneur · o objet. Si quelqu'un modifie un seul caractère, sig ne correspond plus : refusé.

4 · Le chiffrement

Toujours actif

SSE, AES 256 bits, sur Blob, Files, Queue, Table et disques managés. Chiffre à l'écriture, déchiffre à la lecture, ne se désactive pas, gratuit, sans perte de performance.

Clé Microsoft (défaut)

Rien à gérer. Microsoft fait la rotation.

Clé client

Dans Key Vault ou un HSM managé (FIPS 140-2 niveau 3). Tu crées, désactives, fais tourner et audites la clé. Coffre et compte dans la même région, abonnements différents possibles.

➕ examen : le Key Vault d'une clé client doit avoir la suppression réversible et la protection contre le vidage activées, et le compte doit avoir une identité managée avec le droit de lire la clé. ➕ Chiffrement d'infrastructure = un 2e chiffrement, choisi à la création du compte seulement. ➕ Azure Disk Encryption (BitLocker / dm-crypt) chiffre dans la VM : c'est autre chose que SSE.

5 · Surveiller et détecter

📊 Storage Insights

Vue unifiée performance, capacité, disponibilité : latence, débit, transactions. Journaux d'activité pour l'audit. Passif : il montre ce qui s'est passé.

🛡️ Microsoft Defender for Storage

Actif : analyse les blobs envoyés (logiciels malveillants), repère les données sensibles mal rangées, alerte sur les accès anormaux (volume d'envoi suspect, IP inhabituelle).

6 · ➕ En CLI

az storage container generate-sas --account-name stock1 -n manifestes \
  --permissions r --expiry 2026-11-11T12:00Z --https-only --as-user --auth-mode login
az storage container policy create --account-name stock1 -c manifestes -n lecture-1j \
  --permissions rl --expiry 2026-11-12T00:00Z
az storage account keys renew -g rg-labo -n stock1 --key key1
az storage account update -g rg-labo -n stock1 --allow-shared-key-access false

--as-user --auth-mode login = SAS de délégation d'utilisateur. keys renew = régénérer une clé (invalide toutes les SAS signées avec). L'exercice du module : créer un compte, un conteneur Blob sécurisé et un partage Files, puis les gérer avec le navigateur de stockage du portail.

🚛 Appliquer à Optifuel

Comment l'app et les chauffeurs touchent aux manifestes sans jamais voir une clé.

  • L'app (sur AKS ou k3s) lit et écrit avec une identité managée + le rôle Contributeur aux données Blob du stockage sur le seul compte. Clé partagée désactivée.
  • Le chauffeur envoie son scan directement depuis la PWA : le serveur lui génère une SAS de délégation d'utilisateur en écriture seule (sp=cw), valable 10 minutes, sur un seul blob. Le fichier ne transite pas par ton serveur.
  • Pour montrer un manifeste au répartiteur : une SAS en lecture seule de quelques minutes.
  • Defender for Storage analyse les fichiers envoyés : utile quand des chauffeurs téléversent depuis leur téléphone.

💡 C'est exactement ce que demandent les banques : aucun secret stocké, accès minimal, durée courte.

Pièges d'examen

🪤« Une SAS a fuité ; je la supprime dans le portail. »Une SAS ne se « supprime » pas. Si elle utilise une stratégie d'accès stockée, modifie ou supprime la stratégie ; sinon régénère la clé qui l'a signée.
🪤« La SAS la plus sûre est la SAS de compte. »La plus sûre est la délégation d'utilisateur (signée avec Entra ID), mais pour Blob seulement.
🪤« Je désactive le chiffrement au repos pour gagner en performance. »SSE ne se désactive pas et ne coûte rien en performance.
🪤« Ma SAS commence « maintenant » et échoue les premières minutes. »Décalage d'horloge : mets le début 15 min dans le passé ou aucun.
🪤« Je mets ma clé gérée par le client dans un Key Vault d'une autre région. »Même région obligatoire (l'abonnement peut différer).
🪤« sp=rwdl donne seulement la lecture. »r lecture, w écriture, d suppression, l liste : c'est presque tout.

Encart Terraform

🟪 Accès sans clé : identité managée + rôle de données

resource "azurerm_user_assigned_identity" "app" {
  name                = "id-optifuel-app"
  resource_group_name = azurerm_resource_group.labo.name
  location            = "canadacentral"
}
resource "azurerm_role_assignment" "blob" {
  scope                = azurerm_storage_account.manifestes.id
  role_definition_name = "Storage Blob Data Contributor"
  principal_id         = azurerm_user_assigned_identity.app.principal_id
}
# Clé gérée par le client : bloc customer_managed_key dans azurerm_storage_account
# (Key Vault avec purge_protection_enabled = true)
